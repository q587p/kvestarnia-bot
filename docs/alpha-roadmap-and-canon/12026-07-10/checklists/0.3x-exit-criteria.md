# Exit criteria для `0.3.x`

Цей checklist визначає готовність лінійки **Closed Alpha Readiness**. Він не вимагає, щоб гра була «завершена», і не гарантує конкретної кількости тестерів.

## 1. Поточна versioned робота

- [ ] `0.3.6 Bureaucramancer Personal Protocol` має узгоджений task scope.
- [ ] Focused tests покривають filing, signing, mana spend, concurrency, stale callbacks, remort boundary і boss trigger replay.
- [ ] Проведено незалежний deep review змінених файлів.
- [ ] Усі blocker/important findings виправлено до merge або роботу не визнано merge-ready.
- [ ] Жоден unrelated feature не доданий до `0.3.6` як «маленький follow-up».
- [ ] Merge/deploy status записаний фактично, без припущення з назви branch/task.

## 2. Правдива продуктова поверхня

- [ ] Root README більше не називає `0.2.0` наступною роботою.
- [ ] Product brief описує current persistent combat, social і progression surfaces.
- [ ] Roadmap називає `0.3.x` поточною Closed Alpha Readiness line.
- [ ] Tasks index відрізняє shipped, active, queued, superseded і archived.
- [ ] Balance docs мають одну канонічну формулу знаку характерника.
- [ ] `docs/ai/context.md` відповідає актуальному main і власному ліміту рядків.
- [ ] Public site не обіцяє flagged/unknown-production feature як доступну.
- [ ] Визначено canonical site URL або чесно зафіксовано, що стабільного URL ще немає.
- [ ] Local Markdown links перевірені після архівації/переміщень.

## 3. Feature maturity і production facts

- [ ] Є sanitized matrix: implemented / default / production-enabled / manual-QA status.
- [ ] Значення production flags отримані з дозволеного operational source, а не виведені з `.env.example`.
- [ ] Невідомі production факти позначені як `unknown`.
- [ ] Feature flags мають власника та rollback/disable спосіб.
- [ ] Dev grant/reset helpers підтверджено вимкненими для production або це позначено blocker-ом.

## 4. Manual Telegram QA

- [ ] Чароковальня: duplicate attempt, stale preview, donor, equipped upgrade і attunement.
- [ ] Турніри: scoring, repeated-opponent limit, period rollover/display і reward replay.
- [ ] Знак характерника: placement/support replay, final roster і кілька broad activations.
- [ ] Протокол бюрокроманта: filing/signing replay і персональний trigger.
- [ ] Quest Overview: outside access, table presence, first-step reward і current quest rows.
- [ ] Quest Iskrokamin: fresh/replay item grants без reroll/duplicate.
- [ ] Mantok gear actions: solo, two-enemy, Big Barrel і turn-based duel.
- [ ] Yeger bandage preview/confirm/cancel/replay.
- [ ] Inventory, Mantok Chest і item upgrade hot paths не мають player-visible regression.
- [ ] Усі fail/blocker результати записані з reproduction steps і власником.

## 5. Performance evidence

- [ ] Після `0.3.5` зібрано репрезентативний набір sampled/slow route timings.
- [ ] Для instrumented routes розділено DB, compute і Telegram time.
- [ ] Row/item counts присутні там, де вони потрібні для діагностики.
- [ ] Production logs не містять player-facing text, callback tokens, large JSON або secrets.
- [ ] Рішення про raw Telegram user id у performance logs переглянуто за принципом data minimization.
- [ ] Є ranked top findings із доказом; speculative Redis/queue/database migration не відкриті без потреби.
- [ ] Якщо P0/P1 regression знайдено, він має окрему вузьку task і regression test.

## 6. Data safety та operations

- [ ] Документовано фактичний production storage target.
- [ ] Backup runbook відповідає цьому target.
- [ ] Backup створено способом, безпечним для фактичного storage/process model.
- [ ] Restore проведено на окремій копії або середовищі.
- [ ] Записано дату restore proof та відповідального.
- [ ] Визначено retention/storage місце без public access.
- [ ] Є короткий incident flow для duplicate rewards, data corruption і economy exploit.
- [ ] Відомо, як тимчасово вимкнути reward-bearing/raid features без втрати canonical state.

## 7. Feedback та вимірювання альфи

- [ ] Є добровільний feedback path.
- [ ] Player-facing privacy copy пояснює, що відправляється.
- [ ] Feedback read/export доступний лише дозволеній ролі.
- [ ] Feedback не дає gameplay reward або public status.
- [ ] Визначено activation funnel.
- [ ] Визначено D1/D7 return без прихованої зміни gameplay.
- [ ] Є aggregate social metrics для duel/party/raid.
- [ ] Є economy snapshot для gold, Iskrokamin, medical items, upgrades і tournaments.
- [ ] Reports не показують персональні або tiny-cohort rows.
- [ ] Analytics/reporting failure не блокує gameplay settlement.

## 8. Керований rollout

- [ ] Перша мала хвиля має owner, observation window і support channel.
- [ ] Blocker/data-loss/duplicate-reward findings із хвилі закрито до розширення.
- [ ] Наступна хвиля не запускається лише через календарну дату.
- [ ] Фактична кількість тестерів записується після rollout, а не припускається roadmap-ом.
- [ ] Визначено п’ять найбільших friction points або чесно зафіксовано, що даних ще недостатньо.

## 9. Scope і release discipline

- [ ] Кожна versioned task має один primary outcome.
- [ ] Кожна task має explicit non-goals.
- [ ] Risky in-scope fixes виправляються до merge.
- [ ] Unrelated findings не потрапляють у release без re-scope й повторного review.
- [ ] Player-visible зміни мають task, changelog/release surfaces і manual QA.
- [ ] Docs-only reconciliation не створює фальшивий numbered gameplay release.
- [ ] Наступний номер визначається лише після перевірки актуального `main`.

## 10. Go / no-go

### `GO` до закриття `0.3.x`, якщо

- усі P0 секції пройдено;
- немає відкритого data-loss або duplicate-reward blocker;
- backup restore доведений;
- критичний smoke має прийнятний результат;
- відомі performance/economy ризики мають власників;
- проведено хоча б одну керовану хвилю спостереження;
- Maintainer явно погодив наступну product line.

### `NO-GO`, якщо

- production стан виводиться лише з repository defaults;
- manual QA позначений pending для ризикової current feature без явного прийняття ризику;
- restore proof відсутній;
- review findings відкладаються «на після merge»;
- наступна feature line потрібна лише для заповнення номера версії;
- немає способу отримати feedback або зрозуміти основний friction.
