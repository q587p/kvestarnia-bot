# `0.4.x` і наступні місяці

## Передумова

Цей roadmap активується лише після проходження [`../checklists/0.3x-exit-criteria.md`](../checklists/0.3x-exit-criteria.md). Він не є дозволом реалізовувати всі перелічені фічі поспіль.

Горизонт плану: приблизно `2–4` місяці після закриття `0.3.x`. Строки залежать від live usage, відгуків, performance і economy evidence.

## `0.4.x` — Party Roles & Group Goals

### Продуктова мета

Перетворити вже наявний Big Barrel Brother proof із «одного гуртового бою, що технічно працює» на повторювану соціяльну мету, де різні класи мають читабельні ролі, а гравці мають причину зібратися ще раз.

Необхідний результат лінійки:

- рейдові ролі не перекривають одна одну;
- одна й та сама damage event не зменшується двічі випадково;
- UI пояснює активні ефекти без формул і довгих журналів;
- кілька персонажів одного класу не дають нескінченний контроль;
- reward settlement лишається replay-safe і не множиться за кількістю target/add rows;
- групову активність можна повторити з попереднім гуртом без повної ґільдійної системи.

## Рекомендована послідовність `0.4.x`

### 1. Raid Role Interaction Contract

Спершу — вузький design/architecture slice, а не нова бойова кнопка.

Зафіксувати:

- typed boss action scopes: personal, broad/all-party, mixed component;
- пріоритет target selection, redirect, immunity, mitigation, shield і damage application;
- взаємодію знаку характерника, протоколу бюрокроманта та майбутнього Taunt;
- deterministic conflict rule для кількох акторів;
- журналювання stored outcome, а не повторне обчислення під час replay;
- simulation fixtures для малих і повних складів.

Власники: game/balance designer, Main Codex, Review Codex.

Готово, коли interaction matrix і characterization tests дозволяють додавати одну роль без умовних гілок по локалізованому тексту.

### 2. Warrior Raid Taunt

Реалізовувати лише після interaction contract і balance simulation.

Поточний draft із трьома boss responses та п’ятьма ходами cooldown потребує перевірки:

- фактичний uptime одного Воїна;
- почерговий Taunt двох Воїнів;
- перетворення broad attack на один hit;
- взаємодія з персональним протоколом після redirect;
- чи не робить Taunt знак характерника невидимим або непотрібним;
- що стається, якщо Воїн падає до target selection;
- чи не зберігається cooldown/effect після terminal/restart неправильно.

Кандидат release name: **`Warrior Raid Taunt`**.

### 3. Один новий груповий виклик

Обрати лише один напрям за результатами usage:

- **`Big Barrel Targetable Adds`** — якщо гравцям бракує тактичного вибору;
- **`Second Group Objective`** — якщо потрібна різноманітність, а не складність одного боса.

Не реалізовувати обидва в одному release. Новий target/add не повинен автоматично множити XP, gold або loot.

### 4. Party History and Regrouping

До ґільдій корисніше перевірити менший social convenience loop:

- recent opt-in party history;
- повторне запрошення відомих учасників;
- без публічного location/online leak;
- без постійного guild rank, податків або спільного банку;
- bounded history і explicit consent.

Це доводить, чи гравці справді хочуть стабільні групи.

### 5. Group Progress Review

Після кількох тижнів даних відповісти:

- скільки party sessions створюються і стартують;
- скільки завершуються;
- який roster size типовий;
- чи повертаються ті самі групи;
- чи є class-role skew;
- чи не витісняють raid rewards solo loop.

Тільки після цього вирішувати, чи потрібна `0.5.x/0.6.x` ґільдія.

## Rogue Reputation — спершу redesign

Поточний draft додає durable penalty, але не визначає повний player loop. Перед implementation потрібен короткий product/design task **`Rogue Heat and Rumor Loop`**:

- що шкала змінює на практиці;
- як вона відновлюється;
- де ризик дає цікавий вибір, а не лише покарання;
- що бачить сам Злодій;
- чи зберігається вона після remort;
- як уникнути public shame;
- чи потрібна позитивна репутація окремо.

Без відповідей не створювати schema/ledger лише «на майбутнє».

## `0.5.x` — Collections, Economy & Season Zero

Точний порядок визначається метриками `0.3.x–0.4.x`, але рекомендовані кандидати такі.

### Bestiary Collection MVP

Найбезпечніший довгий retention loop, якщо combat повторюється, а гравці вже читають Бестіарій:

- лише доведені encounter/win/trophy records;
- без вигаданого backfill;
- без power reward;
- private by default;
- компактний progress card і одна rewardless milestone family.

### Old Altar Gold-only MVP

Активувати лише після economy snapshot.

Перший slice:

- gold offering;
- bounded current-life favor;
- одна коротка Priest-selected-stat blessing;
- без item sacrifice, окремої локації, resurrection або loot multiplier;
- чіткий sink, а не новий reward faucet.

Item offerings залишити окремим follow-up після перевірки ownership/reservation UX.

### Consumable Use Audit

Спершу інвентаризація:

- які consumables мають реальну дію;
- які є flavor/junk;
- які player cards обіцяють дію, якої немає;
- які effect families можна підтримати без broad shop.

Після audit — один вузький use family або take-away drink shelf, але не обидва разом.

### Season Zero

Перший сезон має бути контентним експериментом, не новим framework:

- одна тема;
- одна група authored scenes/monsters/items;
- один bounded group або solo milestone;
- rewardless/cosmetic recognition;
- без FOMO-critical power;
- чітка дата завершення й післясезонний підсумок.

## Можлива ґільдія — лише discovery

Повний guild MVP не є автоматичним кроком після raid roles. Спершу потрібні докази:

- гравці регулярно формують повторні party;
- social retention кращий у повторних груп;
- є запит на назву/identity, а не лише на зручне повторне запрошення;
- moderation і offensive-name handling мають власника;
- shared rewards не створюють pressure або abuse.

Якщо доказів немає, лишити party history/regrouping і не будувати guild schema.

## Технічний супровід протягом `0.4.x–0.5.x`

### Behavior-preserving decomposition

Великі application/presenter/repository файли декомпонувати тільки навколо активної зміни й characterization tests:

- не робити repository-wide rewrite;
- зберігати публічні service contracts;
- не переносити Telegram types у domain;
- не змінювати transaction ownership у refactor-only release;
- окремо перевіряти reward/resource exactly-once boundaries.

### Storage decision

Не мігрувати з SQLite лише через припущення. Рішення про PostgreSQL або іншу інфраструктуру має спиратися на:

- виміряний write contention;
- scheduler lag;
- backup/restore вимоги;
- storage growth;
- реальну потребу в кількох процесах/instances.

### Platform scope

Mini App, повний web client та інші месенджери залишаються пізніми напрямами. Public site може ставати кращою вітриною, але не другим game client у цьому горизонті.

## Stop conditions

Поставити нову feature line на паузу, якщо з’являється хоча б одне:

- неперевірений data-loss або duplicate-reward ризик;
- немає restore proof;
- performance regression не можна розкласти на DB/compute/Telegram;
- manual QA борг накопичується швидше за нові релізи;
- economy snapshot показує runaway source/sink;
- нова фіча не має визначеного player problem або acceptance evidence.
