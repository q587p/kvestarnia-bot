# ПЛАН: Combat Action Variants

## Навіщо це потрібно
Зараз `/fight` у Квестарні ще лишається combat probe: короткою, безпечною перевіркою кнопок і reward flow. Це добре для MVP, але вибір дії все ще надто плаский: гравець бачить майже одну й ту саму «атакуй/вийди» логіку, а mana/resource-мови ще не вистачає, щоб закласти майбутні класи, спели й трішки характеру в сам бій.

Цей документ описує перший маленький slice, який переводить fight UI й домен до **typed action variants** без переходу в повний persistent combat.

## Цілі першого slice
- Замість одного «узагальненого удару» показати кілька типів бойових дій.
- Відобразити ресурсну ціну дії в UI, якщо вона є.
- Дати місце для race/class/combo flavor, але без «єдиного правильного білду».
- Зберегти нинішній combat probe детермінованим, коротким і тестованим.
- Не ламати idempotency: повторний callback не має вдруге списувати mana або видавати нагороду.

## Не цілі першого slice
- Не запускати повний turn-based combat engine.
- Не зберігати окремий persistent combat state.
- Не вводити healing/rest loop, damage-over-time, status effects або cooldown economy.
- Не робити повну equipment-математику всередині fight.
- Не будувати group raid, PvP або boss system на цій же PR.

## Таксономія дій

### `physical`
- Базова дія для сили, зброї й простого тиску.
- Добре підходить воїну, єгерю, частині орків і «просто вдарити».
- Ресурсна ціна здебільшого нульова, якщо інше не задає клас або контекст.

### `spell`
- Дія для інтелекту, мани й коротких заклять.
- Має показувати витрату mana прямо в кнопці або підписі.
- Для раннього slice достатньо 1-2 магічних дій.

### `social` / `trick`
- Дія для харизми, спритності, вдачі, блефу або комедійного контролю.
- Менша пряма шкода, зате може давати debuff, stun-like flavor, bonus reward або tactical edge.
- Добре пасує барду, бюрокроманту, злодію й «м’яким» сценам.

### `class-special` (optional)
- Не обов’язковий для всіх.
- Може з’явитися лише в окремих класів, якщо є чіткий flavor і мала балансна вартість.
- На першому етапі краще мати 1-2 приклади, а не універсальну систему талантів.

## Як змінюються назви дій
Race/class/combo можуть:
- змінювати назву кнопки;
- змінювати короткий flavor після дії;
- додавати малий modifier до шкоди, шансів або ресурсу;
- відкрити `class-special` для окремого класу.

Вони не повинні:
- робити один build очевидно правильним;
- вбивати цілі класи без mana;
- робити race/class бонуси настільки великими, щоб гравець почувався «змушеним» до одного шляху.

Добре: `Козак-характерник` отримує інший текст і трохи кращу фізичну дію.  
Погано: `Козак-характерник` раптово має +40% усього, а всі інші — тільки сльози й UI.

## Як показувати ресурси
Якщо дія витрачає ресурс, це має бути видно до натискання або відразу в підписі кнопки.

Приклади:
- `🔮 -2 мани`
- `❤️ -1 HP`
- `🪙 -1 золото` тільки якщо колись з’явиться платна дія

Правило: якщо користувач бачить «магічну» дію, він має зрозуміти, що вона коштує і що саме.

## Ідемпотентність і stale callbacks
Повторне натискання тієї ж кнопки не повинно:
- ще раз списати mana;
- ще раз видати XP/gold/item;
- змінити стан, якщо попередня дія вже зарахована;
- падати з незрозумілим 400/422 помилками.

Рекомендація для майбутньої реалізації:
- callback data має містити версію і короткий action id;
- сервер має мати окрему action claim / action log перевірку перед будь-яким списанням ресурсів;
- stale callback повинен повертати коротке «вже зараховано» або «дія вже неактуальна».

## Запропонована форма callback data
Для першого slice достатньо коротких, людяних токенів:

```text
v1:fight:probe:mimic:attack
v1:fight:probe:mimic:spell
v1:fight:probe:mimic:trick
v1:fight:probe:mimic:flee
```

Якщо пізніше combat стане stateful, краще перейти на:

```text
v1:combat:{combatId}:{actionId}
```

Головна вимога: не перевищити Telegram callback data limit і не заховати в callback половину бізнес-логіки.

## Тест-план для майбутньої PR

### Unit
- кожен action variant мапиться в правильний type;
- mana cost рахується стабільно;
- race/class/combo modifiers не виходять за дозволений діапазон;
- fallback-дія працює без класу або при невідомому state.

### Integration
- callback parser приймає валідний action;
- повторний callback не дублює reward або mana cost;
- stale callback повертає контрольовану відповідь;
- fight presenter і bot handler показують однаковий action label.

### Manual QA
- відкрити `/fight`;
- натиснути кожну бойову кнопку;
- натиснути ту саму кнопку вдруге;
- перевірити, що mana/XP/gold/item не подвоюються;
- перевірити, що різні класи бачать різні, але короткі й зрозумілі підписи.
