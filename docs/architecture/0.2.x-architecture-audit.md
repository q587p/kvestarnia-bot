# Kvestarnia `0.2.x` Architecture Audit

Status: proposed input for `0.2.2`  
Audit baseline: `main` at package version `0.2.0`, commit `bb3e03204ba14d2ea80eaff2a3fa39e04791ea94`  
Revalidation point: rerun this inventory after `0.2.1 — Multi-Enemy Foundation` lands

## `0.2.2` revalidation

Revalidated after `0.2.1 — Multi-Enemy Foundation` landed on `main` at `a4622e4`.

The post-`0.2.1` tree confirmed the same P0 hotspots: central bot assembly and executable composition remained the safest behavior-preserving architecture target before Threat Escalation. `0.2.2` therefore implemented the modular bot runtime and explicit composition/lifecycle layer without changing `FightService` internals, combat formulas, stored combat JSON, callback payloads, Prisma schema or player-facing runtime copy.

Final PR pass: the central `src/bot/featureRegistrars.ts` compromise was removed. Feature ownership now lives in `src/bot/modules/core.ts`, `character.ts`, `inventory.ts`, `tavern.ts`, `quest.ts`, `combat.ts` and `social.ts`; architecture tests pin registrar order, command/alias inventory, callback-prefix ownership and module import cycles. `createRuntime.ts` now uses an explicit lifecycle state so `start()` is idempotent, concurrent `stop()` calls share cleanup, stop-before-start prevents later resource startup, schedulers stop before bot shutdown, and health/Prisma cleanup still runs if `bot.stop()` rejects.

## Executive verdict

The project has healthy architectural intent and unusually strong correctness discipline for its size:

- explicit `bot` / `services` / `domain` / `db` / `content` boundaries;
- repository interfaces in front of Prisma;
- pure combat/domain primitives;
- strict TypeScript, Vitest, ESLint and one broad `npm run check`;
- durable state, replay-safe callbacks and transaction-oriented reward handling;
- no unnecessary framework or production dependency sprawl.

The main problem is not a failed architecture. It is **concentration of orchestration** as the playable surface grew.

Two files have become change magnets:

- `src/bot/createBot.ts`: roughly 4.4k lines;
- `src/services/fightService.ts`: roughly 4.2k lines.

The highest-value near-term work is a behavior-preserving modularization pass, not a rewrite.

## What this audit does not claim

There is no profiling evidence in this review that Node.js, grammY, Prisma or SQLite are the current runtime bottleneck. Therefore this package does not promise lower latency or higher throughput.

The intended optimization is:

- lower review and merge-conflict cost;
- safer middleware and callback registration changes;
- clearer ownership;
- smaller test surfaces;
- easier future multi-enemy, threat and party work;
- startup wiring that can be tested without importing the whole production process.

Runtime performance work should start only after route latency, query count and event-loop delay are measured.

## Current strengths to preserve

### 1. Domain boundary

`src/domain/` is intentionally Telegram-free. Combat receives ordinary data and returns ordinary state. This is the right foundation for simulations, duels, solo fights and later party combat.

Do not move grammY context, callback payloads or presenters into domain modules during the refactor.

### 2. Repository boundary and transaction safety

Repository interfaces keep Prisma details below services. Recent gifting, barter, chest, Shynok and combat work already treats stale callbacks, replays, reservations and exactly-once effects as first-class requirements.

Do not replace these narrow repositories with a generic repository, ORM wrapper or event bus.

### 3. Small dependency surface

The runtime dependency set is intentionally small. The architecture pass does not need NestJS, Inversify, tsyringe, a router package, CQRS tooling or a new validation framework.

### 4. Existing extraction pattern

`src/bot/presence/presenceRouting.ts` shows that pure-ish route classification can be moved out of `createBot.ts` and tested without moving gameplay logic into the bot adapter. The same incremental pattern should be used for middleware and module registration.

## Hotspot inventory

| Area | Evidence | Risk | Priority |
|---|---|---|---|
| Bot assembly | `src/bot/createBot.ts` imports commands, parsers, keyboards, presenters, services and middleware policy; registers roughly two dozen callback namespaces | high fan-in/fan-out, merge conflicts, accidental registration-order changes | P0 |
| Combat application service | `src/services/fightService.ts` owns starter probe, persistent session start/turn/timeout, settlement, rewards, encounter policy, problem quest chain, passage rules, recovery, analytics and source integration | multi-enemy work can multiply branching and make transaction boundaries harder to review | P1 |
| Composition root | `src/bot.ts` constructs repositories and services directly and starts process resources at module scope; several constructors use positional `undefined` placeholders | startup is hard to test; dependency mistakes are easy; lifecycle ownership is implicit | P0 |
| Cross-cutting route policy | presence classification and combat/pending-raid allowlists are maintained in separate string-prefix branches | policy drift can stamp the wrong presence or bypass/block a route | P1 |
| Optional capabilities | code sometimes checks `typeof service.method === "function"` | contracts are partly structural and mocks can hide missing production capabilities | P2 |
| Large schema/docs | Prisma schema and canonical plans are long but still coherently organized | maintenance cost, not an immediate correctness blocker | P3 |

## Hotspot 1: `createBot.ts`

The file currently performs several distinct jobs:

1. declares bot-facing service and option contracts;
2. creates the grammY bot and error handler;
3. installs message freshness and cross-cutting middleware;
4. registers all commands;
5. registers callback namespaces and parser failure behavior;
6. handles feature callbacks;
7. renders or edits Telegram messages through presenters and keyboards;
8. owns combat-lock redirection and pending-raid gating;
9. owns presence refresh helpers and location routing;
10. resumes a bot-bound notification scheduler.

That combination makes almost every feature PR touch one central file even when the feature already has separate command, callback, keyboard and presenter modules.

### Consequences

- unrelated feature branches conflict;
- a reviewer must scan a large import block and distant handler body;
- middleware order is visible but fragile;
- ownership of a callback namespace is not obvious from the directory tree;
- a small callback addition expands the largest file;
- tests tend to exercise broad behavior instead of a local registrar.

### Recommended response

Keep `createBot()` as the public assembly function, but make it a shell that:

- creates the bot;
- installs cross-cutting middleware in an explicit order;
- calls a short ordered list of coarse feature registrars;
- resumes the one bot-bound notification process;
- returns the bot.

Do not create one file per individual callback. Use 5–8 coherent modules.

## Hotspot 2: `FightService`

`FightService` is still useful as a stable application facade, but its implementation now spans unrelated policies and workflows.

Mixed responsibilities include:

- level 1–2 starter combat probe;
- level 3+ persistent combat lookup and start;
- passage preview and encounter memory;
- turn CAS and timeout resolution;
- zero-HP terminal repair;
- resource settlement;
- reward generation and replay;
- problem quest issue/progress/turn-in;
- monster-rest behavior;
- difficulty and monster selection;
- Yeger/adventure source behavior;
- drink modifiers and analytics;
- some display-oriented skill labeling.

### Near-term decision

Do **not** deep-split `FightService` in the same release as bot modularization unless `0.2.1` makes it impossible to preserve behavior cleanly.

For `0.2.2`, establish clean bot/application seams and leave a dedicated follow-up task. A facade-preserving combat split is safer than changing the bot wiring and combat transaction orchestration together.

### Desired later shape

Keep `FightService` as the API consumed by commands and schedulers while moving implementation behind focused collaborators:

- encounter coordinator;
- session/turn coordinator;
- settlement coordinator;
- reward coordinator;
- problem quest coordinator;
- pure encounter/reward/difficulty policies.

Transaction ownership must remain explicit. Do not decompose one transaction across loosely coordinated services.

## Hotspot 3: `src/bot.ts`

The entry point currently creates Prisma repositories, creates services, starts the health server, creates the bot, starts schedulers, installs process signal handlers, updates Telegram commands and sends deploy notifications.

This works, but all production composition is bound to import-time execution.

### Risks

- an import can start or allocate process resources;
- startup dependencies are difficult to unit test;
- repository/service construction is a long positional list;
- shutdown ordering is implicit;
- adding another scheduler makes the entry point grow.

### Recommended response

Introduce a tiny application layer:

- `createRepositories(prisma)`;
- `createServices(repositories, config)`;
- `createRuntime(dependencies)`;
- explicit `start()` and `stop()` ownership.

Keep `src/bot.ts` as the executable entry point. Do not introduce a dependency-injection container.

## Route-policy drift risk

Presence routing already classifies commands and callback prefixes. Combat lock and pending raid behavior separately inspect route strings and callback prefixes.

These policies have different purposes, so they should not be merged blindly. In `0.2.2`:

- move each policy to a named module;
- preserve logic byte-for-byte where practical;
- add characterization tests for representative allowed and blocked routes;
- document middleware order.

A later task may introduce one shared route classifier if it can prove parity. The architecture release should not redesign route semantics.

## Priority plan

### P0 — `0.2.2`

- modular bot registrars;
- extracted middleware;
- testable composition root and lifecycle;
- architecture boundary tests;
- no behavior, schema or callback contract changes.

### P1 — next free `0.2.x` if needed

- facade-preserving combat application decomposition;
- named dependency objects for high-arity services;
- pure policy extraction backed by characterization tests.

### P2 — after stable evidence

- shared route classification;
- explicit service capability contracts;
- callback latency/query-count instrumentation;
- targeted DB query batching based on measurements.

## Approaches explicitly rejected

- repository-wide rewrite;
- microservices;
- NestJS or a DI container;
- generic event bus for ordinary synchronous flows;
- generic repository abstraction over Prisma;
- moving Telegram types into domain;
- broad folder renames;
- path aliases solely to shorten imports;
- combining architecture refactor with threat escalation;
- changing stored combat JSON shape in a behavior-neutral refactor;
- enforcing architecture only through arbitrary line-count limits.

## Success signal

The architecture pass is successful when a new feature normally changes:

- one feature registrar;
- its existing command/callback/presenter/keyboard files;
- its service/domain/repository files;

and does **not** require editing a 4k-line central router unless it changes a true cross-cutting policy.
