# Recommended `0.2.x` Sequence

Status: proposed adjustment after `0.2.0`

## Baseline order in current docs

The current roadmap places:

1. `0.2.1` — Multi-Enemy Foundation;
2. `0.2.2` — Threat Escalation;
3. `0.2.3` — Item Tags / One-Use Manatky.

## Recommended order

### `0.2.1` — Multi-Enemy Foundation

Keep the existing product slice.

It should own only the backward-compatible multi-enemy state/engine foundation and exactly-two-enemy runtime promised by its eventual task. It should not also modularize the whole bot.

At closeout, record:

- which files grew most;
- whether `FightService` gained new orchestration branches;
- whether stored combat state now has an explicit version/compatibility reader;
- whether callback and presenter contracts stayed stable.

### `0.2.2` — Architecture Stabilization

Behavior-preserving release:

- modular bot registrars;
- extracted cross-cutting middleware;
- explicit application composition root;
- explicit runtime lifecycle;
- architecture boundary tests;
- documentation of route ownership.

No gameplay, balance, schema, callback payload or stored-state changes.

### `0.2.3` — Threat Escalation, preferred path

Proceed if the `0.2.1` closeout shows that multi-enemy start/turn/settlement/reward behavior remains understandable and does not require broad edits across one giant method cluster.

Threat Escalation then reuses the stable module boundaries from `0.2.2`.

### Conditional `0.2.3` — Combat Application Decomposition

Use the next free version for `docs/tasks/0.2.x-combat-application-decomposition.md` instead of Threat Escalation if any of these are true after `0.2.1` and `0.2.2`:

- ordinary fight start, turn, timeout, settlement and reward logic cannot be reviewed independently;
- one change repeatedly edits distant regions of `FightService`;
- multi-enemy compatibility branches are duplicated;
- problem quest, Yeger and ordinary fight integrations require separate copies of the same state transition;
- transaction ownership is unclear;
- focused tests cannot instantiate a narrow combat use case without constructing most of `FightService`.

If this gate triggers:

- `0.2.3` — Combat Application Decomposition;
- `0.2.4` — Threat Escalation;
- `0.2.5` — Item Tags / One-Use Manatky.

This is still within the near `0.2.x` line and is safer than combining behavior and deep refactoring.

### Item Tags / One-Use Manatky

Ship after threat/combat architecture is stable. Do not mix item eligibility contracts with the architecture release.

## Why architecture belongs after `0.2.1`

Doing the bot refactor before `0.2.1` would force the multi-enemy implementation to work against moving paths. Doing it after Threat Escalation would let two complex combat slices accumulate in the current hotspots.

The preferred sequence creates one controlled seam between the state foundation and the behavior expansion.

## Version fallback

If `0.2.2` is already used when implementation starts:

- do not edit historical release entries;
- choose the next free `0.2.x`;
- rename the versioned task doc and release surfaces;
- keep the feature slug `architecture-stabilization`;
- keep artifact filenames independent of PR numbers.

## WIP rule

One implementation branch at a time:

- main Codex implements;
- second Codex reviews read-only;
- no competing architecture implementation branch;
- no parallel Threat Escalation branch until architecture routing settles.
