# 0.4.0 Party-vs-Many Proof QA

Status: automated coverage passes; manual Telegram evidence pending.

## Preconditions

- Use the isolated non-production bot with `GROUP_COMBAT_PROOF_ENABLED=true` and
  party helpers enabled. Keep production configuration and data out of scope.
- Use three local Telegram accounts with current-life characters. Record their
  HP, mana, XP, gold and inventory before each terminal scenario.
- Create fresh party tokens with `/dev_party`; start only through
  `/dev_group_combat <party-token>`. The token is the invite-link suffix after
  `party_`, without the prefix, and only the party leader may start the proof.
- Confirm each fresh active card starts with 23 seconds and then shows the actual
  remaining duration from the unchanged turn deadline after every edit,
  reuses the familiar fight/raid resource layout and groups exact-target action
  buttons two per row. After queuing, the compact confirmation names the current
  plan and action controls remain available so another valid choice can replace it.

## Compact matrix

1. **2×2 happy path.** Start with two joined accounts, choose different enemy
   targets, guard and aid. Expect two private canonical cards, one stored action
   per actor/turn and synchronized next-turn state.
2. **3×3 targeting.** Add the third account and exercise every enemy and living
   injured-ally target. Expect only valid targets in each keyboard; self-aid,
   full-health aid and wrong-side/dead targets must refresh truth without state
   mutation. Concurrent aid must never render `+0 HP`.
3. **Invalid starts.** Try one/four members, a stale-life roster and a member in
   another combat. Expect an explicit blocker and no partial session or group
   lease.
4. **Replace, duplicate and stale input.** Choose one action, replace it before
   the other participants finish, double-tap the replacement and reuse a
   previous-turn button. Expect one actor/turn row containing the latest valid
   choice, one resolution and the current card. Concurrently submit two different
   first choices, then race a replacement against both the final action and timeout;
   the durable row and recap must agree, while identical callbacks remain duplicate.
   Force
   invalidated, no-character, not-found, not-participant and unavailable-actor
   outcomes in focused fixtures; none may answer «Вибір записано».
5. **Final-action race.** Submit the last two choices nearly together. Expect one
   version winner and identical final turn/card state for all participants.
6. **Timeout overlap.** Let one account wait past the visible remaining time
   while another acts at the boundary. Expect one resolution; the missing actor
   guards without item or mana spend.
7. **Deaths, terminal states and journal.** Finish both a win and a loss with different
   actors/enemies reaching zero HP. Expect no revival, no buttons for dead
   targets and an explicit rewardless terminal card. Open the terminal-only
   bounded journal, page through every retained recap row and return to results.
   The same canonical message must show the terminal result and result keyboard
   again even when its delivery revision was already acknowledged; no other
   participant card should refresh.
8. **Process restart.** Restart the local bot after one queued action, after DB
   resolution and before Telegram delivery. Expect the durable pending revision
   to edit the existing private canonical references exactly once, with no
   repeated action, turn, duplicate active card or permanent terminal retry.
9. **Lifecycle locks.** During combat try `/restart`, `/remort` and party roster
   mutation. Expect every participant/roster to remain blocked until terminal
   release; afterward normal lifecycle actions are available again.
10. **Card repair.** Delete one canonical card, press Refresh from another saved
    source and race two refreshes. Expect one replacement reference and deletion
    or inertness of the losing candidate. Start the dev command from a group and
    reuse a stale public party reference; participant cards must still go only
    to each participant's private Telegram DM, and public mutating callbacks
    must be rejected. While combat is active, use an unrelated text command
    once in private and once in a group: private must send a fresh inert
    candidate, CAS-promote it as the sole canonical latest card and retire the
    older reference, while the group receives only a short inert redirect with
    no participant text or mutating keyboard. Buttons from a superseded private
    card must not mutate combat. During replacement-card delivery, verify a
    generic activation error that may have applied buttons leaves the previous
    card inert and the promoted candidate canonical/pending even if candidate
    deletion would fail. A later retry must converge on that candidate with
    exactly one button-bearing canonical message. A failure before activation
    leaves both messages inert until retry; confirmed candidate unavailability
    or failure to inert the previous card may restore the previous reference
    without activating both. A failed old-card deletion after successful
    activation leaves the previous message inert.
11. **Production-like isolation.** Set `NODE_ENV=production` with the proof flag
    still true. Expect no `/dev_group_combat` registration/help row/callback
    mutation and no group-combat scheduler scan.

After win, loss and invalid repair, compare HP, mana, XP, gold and inventory with
the recorded baseline. They must be unchanged; leases and frozen timed statuses
must be released exactly once.

## Regression focus

- Open ordinary single/multi-enemy PvE, Training Doppelganger, a turn duel and
  Big Barrel. Their existing actions, locks, journals and rewards must be
  unchanged.
- Verify `Ситий` and `Натхнення` still pause/release on the older combat modes.
- Review logs only for aggregate errors. No Telegram ids, callback payloads or
  serialized combat state should be emitted.
