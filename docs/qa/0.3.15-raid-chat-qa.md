## Automated matrix

| Area | Required proof |
|---|---|
| Migration | Fresh database and an existing pre-chat database both migrate; existing recruiting/active/terminal raid rows remain readable; schema validation/generation pass; new relations cascade as designed. |
| Repository order | Interleaved player/system entries have monotonic deterministic order; descending-limit query returns newest 13 and the service reverses them to chronological display; 0/1/13/14/130/131 boundaries are covered. |
| Entry dedupe | Same deterministic system source key and same Telegram input source create one entry/revision under sequential retry and real concurrent attempts. A different source with equal body remains a distinct message outside duplicate-body policy. |
| Chat revision | Successful new entry increments `chatRevision` once. Duplicate/no-op/rejected entry does not. Gameplay `PartySession.version` and boss version remain unchanged by pure chat writes. |
| Author/session limits | Fake-clock tests cover 3-second author cooldown, exact remaining time, the fixed first-accepted-post-anchored 42/93-second lineage window and reset, same-author/body 13-second no-op and concurrent CAS claims. Invalid/rate-limited/replayed/no-op outcomes follow the design's exact composer/quota/revision matrix. |
| Hard cap/cleanup | Entry 131 removes only the oldest bounded overflow while monotonic IDs/revision continue; cleanup never loads/deletes unbounded sessions. Terminal 13-day deadline is inclusive/exclusive at exact boundary as documented. |
| Authorization | Joined recruiting, active canonical roster, defeated-but-still-rostered and terminal final-roster reads pass. Invite viewer, outsider, left/removed/withdrawn, changed remort life and post-retention actor cannot make a fresh read. Only recruiting/active authorized states write. `User.currentRaidId` alone grants nothing. Revocation marks durable old-card redaction without pretending already-seen Telegram text can be recalled. |
| Composer creation | Callback is visible/accepted only for an authorized Big Barrel participant with both flags on. An `awaiting_prompt` generation is created before send and exact prompt binding wins by CAS, so slower concurrent callbacks cannot reactivate older prompts. Intent binds actor/session/life/private-chat/prompt ID, lasts 13 minutes and a newer prompt invalidates the old one. Callback data stays within Telegram bounds and rejects malformed/stale tokens. |
| Input routing | Only direct text reply to the exact bot-authored prompt is intercepted. Plain text, commands including `/cancel_raid_chat`, persistent main-menu buttons, reply to inventory/other ForceReply, wrong user/chat, non-reply, media/caption/forward and callbacks continue to their existing route. Cover registration order during active combat/combat lock. |
| Composer lifecycle | Valid reply atomically consumes once. Restart with a bound unexpired prompt still accepts. Cancel, expiry, leave, removal, remort, terminal and flag disable reject the old prompt without mutation. Start-vs-post resolves against the canonical writable state and does not lose/duplicate the message. |
| Invalid correction | Empty, overlong or disallowed-entity reply creates no entry/quota use, issues one clear error plus a newly bound prompt, and makes the old prompt stale. A valid correction succeeds once. |
| Text safety | NFC, trim, newline/tab/multiple-space collapse and the exact prohibited C0/C1/zero-width/bidi list are covered. ZWJ families/professions, variation selectors, combining marks, flags and skin tones survive; grapheme counting is exact at 92/93/94. HTML-looking author/body render escaped; only player names are bold, complete technical event sentences are italic, and no malformed entity or stored HTML appears. |
| Entity safety | Intercepted direct text rejects `url`, `text_link`, `email`, `phone_number`, `mention` and `text_mention`. Attachments, captions and forwarded updates pass to existing handlers without consuming or replacing the composer. An offset-zero `bot_command` likewise routes to the existing command handler. A harmless punctuation string that Telegram did not classify as a forbidden entity remains accepted. |
| Time rendering | UTC persists unchanged; `Europe/Kyiv` output covers winter/summer offsets and seconds. One-date feed uses `HH:mm:ss`; a visible set spanning Kyiv midnight uses `DD.MM HH:mm:ss` consistently. Equal timestamps remain ordered by ID. |
| Telegram budget | Escaping expansion and long names/messages cannot push the complete card beyond 4096 characters. Renderer drops oldest visible chat rows only, preserves newest data/keyboard semantics, changes the header to `останні N із 13` when needed and never splits grapheme/HTML entities. |
| Immediate player notification | Every accepted player post best-effort sends every other current same-life participant one separate escaped HTML message with a bold author and blockquoted body. The author receives no echo. A blocked recipient cannot roll back the entry or sender confirmation; the durable card remains the recovery path. Duplicate/no-op/rejected posts send none. |
| Recruiting presentation | Authorized participant card appends the exact section after the risk paragraph and shows the `💬` compose button. Empty copy and 13-row copy are compact. Invite/nonparticipant presentation contains neither feed nor control. `/online` labels visible sessions as gatherings with canonical `joined/participantCap` occupancy and omits the inactive-raid notice while a gathering exists. Existing one-screen state/reward-risk copy remains truthful. |
| Active presentation | Canonical start creates/repairs one compact chat-card reference per frozen participant; boss card links to chat and chat links back. A knocked-out participant loses combat actions but keeps the chat button plus active read/write access. The feed remains the same `PartySession` lineage; terminal card removes compose and keeps authorized read-only access. |
| Membership system events | Party create, real join, real leave, leader transfer and canonical removal append exactly once in the same transaction. Duplicate join/leave, stale callback and failed eligibility append none. Removal copy exposes no private cause. |
| Preparation system events | Successful ward place/support and Form 13-A/Protocol 13-Z open/sign append exactly once. Insufficient mana, duplicate support/sign, stale/no-op and readiness toggles append none. Existing achievements/resources remain exactly as before. |
| Start/terminal events | Manual and scheduled start each append one start event after winning CAS. Concurrent scheduler/leader attempts create one boss and one event. Win/loss/cancel/expiry append one typed terminal event; failed/replayed settlement appends none. |
| Combat ability events | On the real post-0.3.14 base, allowlisted Taunt/Lament/raid-song/Form 13-B/Dangerous Couplet entries come from the winning resolved round/action summary only. Replaced queued choice, denied choice, ordinary action and replay append none. Starting visible music state is truthful and not inferred from unrelated Shynok performances. |
| Transaction rollback | Forced chat-event insert failure rolls back its paired gameplay transition while enabled; duplicate-source upsert/no-op does not abort a valid replay. Telegram edit failure after commit never rolls back gameplay or chat entry. |
| Durable delivery | Entry/join/start/terminal/revoke transactions set per-participant desired/redaction state. A crash after commit but before fanout is recovered by a bounded startup scan without player interaction. Dirty revision races stay due; broken refs repair for leader and nonleader; retryable and permanent failures follow explicit state transitions without duplicate DB entries. |
| Delivery gating | Bursts across multiple simultaneous raids pass through one fair bounded raid-chat queue, enforce per-target spacing, coalesce to latest revision and never starve a session. Telegram `429 retry_after` persists the exact next due attempt across restart; bounded backoff covers other retryable errors. |
| Redaction | Leave/removal/remort, Big Barrel flag disable and retention expiry schedule recruiting-card scrub and active-card unavailable/delete behavior. Retry and permanent-failure semantics are covered without logging private content; no later refresh can re-expose the transcript. |
| Flag behavior | Raid chat adds no environment/config key and follows `BIG_BARREL_BROTHER_RAID_ENABLED`; disabling that parent surface bounded-scans active refs for redaction, hides fresh UI/reads and blocks writes, preserves rows/raid state, and resumes without retroactive synthetic events. Factory/service wiring is covered. |
| Dev isolation | Local helper can fill 14+, clear, expire composer and accelerate terminal retention. Production never registers, lists or mutates through it under either state of the existing Big Barrel flag. |
| Privacy/observability | Logs/metrics contain event type, result, timing and revision lag only; tests/spies prove no body, prompt text, display name, Telegram ID, invite token or callback payload is logged. No chat entries reach public Chronicle/latest-events surfaces. |
| Gameplay regressions | Posting/reading changes no HP, mana, gold, XP, loot, action, readiness, contribution, reward forecast, achievement or existing ability counter. Existing Big Barrel settlement and 13-round simulations remain green. |
| Read performance | One bounded authorized feed read per card render/fanout snapshot and one bounded recipient query per accepted player post; no per-recipient authorization or entry-query N+1. Delivery can reuse one rendered feed while still authorizing the target roster. |

## Manual Telegram QA setup

- Isolated non-production bot/database.
- `BIG_BARREL_BROTHER_RAID_ENABLED=true`; there is no separate raid-chat flag.
- At least two eligible joined accounts (`A`, `B`) and one eligible outsider (`C`). A second character life/remort path is required for the stale-life case.
- Use the local helper only between cases that explicitly require fill/clear/expiry.
- Record Kyiv timestamp, bot username, git checkpoint and database snapshot/inspection evidence for concurrency/restart/cleanup claims.

## Manual Telegram cases

1. **Empty gathering.** A creates Big Barrel from both the Barrel action and `/raid`. A sees the empty raid-chat section and compose button on the initial participant card; C opening the invite sees neither. `/online` says the group raid is gathering, shows `1/8`, and does not claim that no active raid exists.
2. **Join event.** B joins. A and B see exactly one chronological join row with B's character name. Refresh/reopen does not duplicate it.
3. **Basic exchange.** A presses compose, replies `Хало))` and sees the fresh send confirmation even if the old prompt cannot be edited. Without opening the chat card, B immediately receives a separate message with A's bold name and the escaped body in a blockquote; A receives no echo. B's existing gathering card also updates. B replies; both cards show the same two player rows and timestamps. Player names are bold, message bodies stay regular, and technical rows are italic.
4. **Unrelated text routing.** Open compose, then send a known main-menu button/command and reply to an inventory page prompt. Existing routes still work and no raid entry is created. Return to the exact raid prompt and submit successfully.
5. **Cancel and stale prompt.** Open two compose prompts. Replying to the older one is rejected; `/cancel_raid_chat` cancels the newest without changing raid state; its later reply is rejected.
6. **Content safety.** Try blank/newline-only, 94+ graphemes, HTML-looking text, ZWJ/variation/flag/skin-tone emoji, URL, `@mention`, command, photo, voice and forwarded caption. Valid plaintext/emoji are accepted, commands route normally, forbidden input is not stored, and the card remains valid HTML.
7. **Limits.** Send again inside 3 seconds and exercise the fixed lineage window. Copy shows canonical remaining wait; blocked attempts create no quota/entry and get a corrected prompt. Equal body inside 13 seconds consumes the composer as a no-op without quota/revision.
8. **Last 13 and budget.** Use local fill for 14+ mixed entries including long escaped copy. Newest rows remain oldest→newest and the complete card remains valid; if the budget forces N<13, the header says `останні N із 13`.
9. **Preparation events.** Perform successful ward place/support and Form 13-A/Protocol 13-Z open/sign. Each appears once. Repeat/failed/readiness actions do not add rows.
10. **Leave/privacy.** B leaves recruiting. A sees one leave row. B's old card is durably scrubbed; B and C cannot make a fresh read/write and B's open prompt is stale. Simulate retryable redaction and inspect the retry; if leadership changes, the transfer row is singular.
11. **Restart.** First restart with A's bound compose prompt and verify it still posts once. Separately stop delivery after DB commit but before card edit, restart, and verify the startup dirty-state scan updates both cards without a participant refresh.
12. **Early and automatic start.** Test each on separate sessions. Start row appears once, all active participants receive one compact chat card, and `↩️ До рейду` / `💬 Рейд-чат` navigation works.
13. **Active abilities.** On merged 0.3.14 code, choose then replace a replaceable action; only the actually resolved allowlisted Taunt/Lament/raid-song/Form-song action appears. Ordinary attack/defend/item and failed ability attempts do not.
14. **Active exchange, knockout and failure recovery.** A and B post during battle and receive each other's immediate notifications without opening chat. Knock B out: combat actions disappear, but B still sees `💬 Рейд-чат`, reads the feed and successfully posts another notification. Break one nonleader ref and verify repair. Simulate one blocked notification recipient plus card-delivery `429 retry_after`, restart before due time, and verify the stored post remains successful, no early card retry occurs, and automatic latest-revision delivery follows. Exercise the documented permanent failure class.
15. **Remort/stale life.** Keep a compose prompt, then exercise isolated remort cleanup. Old-life card is scrubbed and fresh read/write fails; historic rows retain the frozen name and do not appear in another raid/life.
16. **Terminal.** Finish win and separately exercise loss/cancel/expiry locally. Exactly one terminal row appears; final roster can read but no compose button/write works. C cannot read.
17. **Retention.** Accelerate the 13-day terminal deadline locally. Final-roster cards are scrubbed, fresh transcript access ends, and bounded cleanup removes chat/composer state without harming the raid record.
18. **Feature rollback.** Disable the existing Big Barrel flag mid-session. Active refs are bounded-scan redacted, every active compose prompt is durably invalidated, controls/fresh reads/write disappear and DB history remains. Re-enable quickly: the old prompt stays invalid, while authorized cards can be rebuilt from history with no fabricated events for the disabled interval.
19. **Production helper isolation.** Inspect production-like command registration/help and attempt the local helper with dev flags both ways. It is absent and creates no database change.
