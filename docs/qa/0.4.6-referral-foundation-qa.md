# QA — 0.4.6 Referral Foundation

Status: release checklist derived from `../../CONTRACT.md`.

## Test setup

Use an isolated non-production bot/database and at least six Telegram accounts:

- **A** — inviter with a current Character;
- **B** — second inviter for rebind/race checks;
- **N** — fresh invitee for the accepted path;
- **D** — fresh invitee for decline/plain-onboarding checks;
- **E** — existing User, including a restart/no-current-Character state;
- **R** — inviter restart/remort and pending-payout recipient.

Use deterministic repository/service fixtures for level jumps, all four milestones, concurrency and volume checks. Any seed/time/level helper must fail closed in production. Record the build SHA, migration, flag values, bot/environment and test evidence without Telegram identity in shared reports.

## Canonical reward matrix

Every automated and manual assertion uses one immutable `ReferralReward` stage bundle with exact `rewardGold` and `rewardItemsJson` values:

| Achievement | `rewardGold` | Exact `rewardItemsJson` |
|---|---:|---|
| `achievement.level.3` | `50` | `1 × item.dense-bandage`; `5 × item.iskrokamin` |
| `achievement.level.5` | `120` | `1 × item.field-kit`; `13 × item.iskrokamin` |
| `achievement.level.8` | `760` | `2 × item.field-kit`; `65 × item.iskrokamin` |
| `achievement.level.13` | `900` | `3 × item.field-kit`; `193 × item.iskrokamin` |

Each row is one all-or-none payout: the gold and every listed item grant commit together or none of them does. No other referral item, premium currency, XP, purchase credit, attempt, cooldown, gear or guild progress is allowed.

## Gate 3 — first touch, acceptance and join notification

### Fresh invitee

- [ ] With presence middleware enabled, N opens A's link as the first bot interaction. The pre-presence serializable capture transaction proves absence and creates the canonical User plus `PENDING` attribution together.
- [ ] Exactly one User and first-touch attribution are created; A and N cannot be the same User. A race with presence/onboarding User creation retries and never backfills an independently created User.
- [ ] Inject failure after the fresh User insert but before attribution insert: both roll back. Retrying A's link creates the one User plus one attribution rather than rejecting an orphan User as existing.
- [ ] Opening B's link before or after the decision never rebinds N.
- [ ] Reopening A's link resumes the same pending/accepted state without a second attribution.
- [ ] Before either choice, the landing identifies A only through the sanitized current Character name or code-generation snapshot, says that A can receive supplies, Iskrokamin and gold at levels `3/5/8/13`, and discloses both visibility surfaces: A may see N's current Character name, current level and four historical stage marks; after first Character creation, Chronicles publicly show the sanitized names of A and N plus their referral relation in `👥 Пригодники`.
- [ ] Plain `/start` and stale onboarding callbacks while N is pending resume consent; authoritative Character creation cannot bypass the choice.
- [ ] Acceptance is explicit and idempotent; decline is terminal for referral attribution but ordinary onboarding remains available.
- [ ] B replays N's accept and decline callbacks: no state changes, no inviter data is exposed and the canonical stale/wrong-owner alert is returned.
- [ ] Accept, decline and Character creation races serialize to one terminal choice; foundation-off still permits continue-without/decline and onboarding.
- [ ] An injected legacy `PENDING + current Character` state cannot accept or receive retroactive stages; the Character and ordinary play remain intact.
- [ ] A valid accepted path reaches Character creation without a click, `/start`, acceptance or Character-creation reward.
- [ ] After a safe Character name exists, A receives one logical join notification naming N and explaining the 3/5/8/13 reward stages.
- [ ] Inject join-outbox insertion failure during first Character creation: Character, `arrivedAt` and event all roll back. Retry commits all three once and only then permits delivery.
- [ ] Join notification replay/reconcile creates one outbox row. An ambiguous Telegram retry may duplicate the external message but cannot change reward state.
- [ ] Two healthy outbox workers race on the join row: one CAS lease/token sends it. Cold start drains a seeded due join row; an expired lease is recovered once.

### Existing, invalid and foundation-disabled paths

- [ ] E opens A's valid link and receives ordinary start routing; no attribution or reward row is created, even when E has no current Character after restart.
- [ ] Same-account self-referral is rejected without attribution.
- [ ] Unknown or malformed tokens do not crash, leak raw token or block onboarding.
- [ ] Unknown, malformed, foundation-disabled, self and existing-user paths create zero attribution; ordinary presence may still create/update the canonical User while onboarding proceeds.
- [ ] Foundation-off blocks new acceptance but preserves accepted relations and their progression.
- [ ] Foundation-off after an accepted arrival does not suppress its committed join outbox; payout-off after a grant leaves its payout notice due/unsent until payout re-enable.

## Gate 5 — automatic payout and retry

### Happy path

- [ ] With payouts enabled and A having a current Character, earning level 3 commits exactly `+50` gold, `+1 item.dense-bandage`, `+5 item.iskrokamin` and `PENDING → GRANTED` in one transaction.
- [ ] If A already owns non-zero stacks of either rewarded item and a non-zero gold balance, payout increments each by the exact frozen delta rather than overwriting any value.
- [ ] The level-5 row grants exactly `+120` gold, `+1 item.field-kit` and `+13 item.iskrokamin`; level 8 grants `+760`, `+2`, `+65`; level 13 grants `+900`, `+3`, `+193` respectively.
- [ ] One invitee completing the full ladder therefore issues exactly `1,830` gold, one dense bandage, six field kits and `276` Iskrokamin stones across four independent stage receipts; aggregate telemetry matches those committed totals.
- [ ] Payout is automatic; there is no claim button, callback or combat/search idle-state requirement.
- [ ] The complete frozen tuple—plan version, milestone, achievement, `rewardGold` and the whole strict item array—matches the immutable issued-policy registry before the winner CAS. Array order is canonical, item IDs are unique, every item exists and every quantity is a positive bounded integer.
- [ ] The uniquely keyed payout-outbox row is inserted in the same transaction as the winner CAS and every gold/item mutation; the Telegram worker sends only after commit and includes the stage/exact bundle plus the current sanitized invitee name when available or the neutral unnamed fallback.
- [ ] Gold, all item stacks, `PENDING → GRANTED`, `actualGrantJson` and payout-outbox insertion commit or roll back together; failure after CAS, after gold, after either item or at outbox insertion leaves the row `PENDING` and every economy value unchanged.
- [ ] Two healthy outbox workers race on a payout notice: one CAS lease/token sends it. Cold start drains a seeded due payout row; an expired lease is recovered once.

### Pending and replacement Character

- [ ] With `REFERRAL_REWARD_PAYOUTS_ENABLED=false`, the entitlement remains `PENDING`, gold and inventory are unchanged and no payout notification says it was received.
- [ ] Re-enabling payouts automatically retries the same row and grants it once.
- [ ] If A has no current Character, the row remains pending without error or redirection.
- [ ] If restart deletes/replaces A's Character during payout, either the complete old-Character bundle wins before deletion or the row stays pending; a later automatic retry grants the whole bundle once to the current replacement Character.
- [ ] If remort resets A's same Character/life/gold/items during payout, serialization puts the entire gold-plus-items bundle wholly before or after that reset; no interleaving or later regrant is possible.
- [ ] Creating A's replacement Character or completing remort wakes and drains pending rewards automatically without an extra `/invite`, claim or manual action.
- [ ] If A restarts after a successful grant, the replacement Character does not receive a replayed copy; a later remort of the same Character likewise does not reissue it.
- [ ] Several pending stages are processed in deterministic bounded batches; every frozen gold and item delta is preserved.
- [ ] More than one scan batch of no-Character and corrupt-bundle rows ahead of a deliverable row cannot starve it: blockers receive capped future `nextAttemptAt` values, keyset scanning reaches the deliverable row, and Character creation wakes that beneficiary immediately.
- [ ] With payouts on, a current Character and a seeded `PENDING` row, cold process start drains the row once without player interaction.
- [ ] Cold-start recovery racing an inviter interaction/reconciler still grants one complete bundle and one logical outbox row.
- [ ] Two concurrent startup recovery workers still grant one complete bundle and one logical outbox row.
- [ ] The real `createRuntime` lifecycle starts one immediate referral scheduler tick, prevents overlapping interval ticks, continues after an isolated tick failure, honors payout flags and stops/cleans up without a trailing mutation. Factory/runtime wiring tests prove the worker is not merely constructed and forgotten.
- [ ] If N restarts while A's reward is pending, later payout still succeeds and uses the neutral notification fallback rather than retaining/leaking a stale invitee name.

### Races and failure isolation

- [ ] Two workers, duplicate callbacks/events, dashboard refresh and reconciler race on one entitlement; one complete gold-plus-items bundle wins.
- [ ] Two distinct level-3 entitlements from different invitees race into A's same existing dense-bandage and Iskrokamin stacks and gold balance: both receipts become `GRANTED`, both logical payout outboxes exist, and the final values are prior gold `+100`, dense bandages `+2` and Iskrokamin stones `+10`, with no lost increment or mistaken `P2002` suppression.
- [ ] Repeat the distinct-entitlement race with both item stacks initially absent. A `CharacterItem` unique collision retries the whole losing transaction and is never misclassified as a replay of the other entitlement.
- [ ] Unique/CAS conflict uses bounded SQLite-compatible retry; zero-row CAS exits or rolls back before gold or inventory mutation and cannot commit a second grant.
- [ ] Service fixtures with a missing plan, malformed/non-array payload, unknown/extra/missing/duplicate item, known valid but wrong item, wrong positive quantity, non-positive quantity, wrong/zero/negative/non-integer/overflowing gold or any other bundle mismatch all fail closed against the immutable issued-policy registry: the row stays `PENDING`, inventory and gold are unchanged, no received notification exists, no component is substituted or partially granted, and bounded operational telemetry is emitted.
- [ ] Failure while creating the entitlement inside the canonical level transaction rolls the whole gameplay transaction back without partial level/reward state; normal gameplay retry commits both once.
- [ ] Failure during post-commit automatic projection leaves the already durable entitlement `PENDING`; retry eventually grants it exactly once without changing the committed invitee level.
- [ ] An ambiguous Telegram API result may retry the external message, but never reopens or duplicates any gold/item mutation.
- [ ] A crash after Telegram accepts either notification but before `SENT` demonstrates the documented rare duplicate-message gap; ordinary concurrent workers without that crash do not double-send.

## Required automated race/integration cases

- two inviters concurrently capture one fresh Telegram user;
- referral first-touch versus presence upsert;
- accept versus decline/replayed callback;
- accept/decline versus authoritative Character creation and stale onboarding callback;
- accepted relation versus foundation flag flip;
- duplicate level event and level jump across multiple milestones;
- two payout workers on the same entitlement;
- an injected zero-row winner CAS after a stale read, proving no gold or inventory increment commits;
- payout versus inviter restart/remort/Character replacement;
- pending retry versus payouts flag flip;
- mixed reward-plan versions racing on the same stable milestone key;
- payout transaction rollback at CAS/gold/each-item/outbox failpoints and post-commit Telegram delivery retry;
- two distinct entitlements concurrently accumulating the same gold balance and existing/absent item stacks;
- User/Character deletion against explicit FK behavior;
- each pre-existing 0.4.5 start-payload route versus referral dispatch.
- referral arrival publication/filtering/dedupe versus milestone/payout absence, plus unchanged `guild.created` Chronicle deduplication.
