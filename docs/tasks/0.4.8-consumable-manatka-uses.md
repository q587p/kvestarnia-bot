# 0.4.8 — Consumable Manatka Uses v1

Status: proposed after group item-action exact-once proof; not implementation-ready
until the curated item/effect allowlist is accepted in this task.

## Goal

Make a tiny curated set of already-owned non-medical consumable manatky actually
usable through the current one-use inventory contract.

Source draft: `docs/tasks/archive/0.2.x-consumable-manatka-uses.md`.

## Activation gate

Amend this task with the exact three or four stable item ids, existing-stack
behavior, use location, numerical effect/cap, metadata migration and remort
policy. Explicitly list rejected generated consumables.

The current `ItemUseOrder` contract is HP-heal-specific. The accepted catalog
must either stay HP-heal-only or explicitly add one typed effect family and its
domain plan, repository/result union, presenter, resource/status, remort and
replay contracts. Do not call mana/comfort support existing, and do not add more
than one new effect family in this slice.

## Scope

- Audit existing authored/generated `consumable` content; do not infer runtime
  behavior automatically from every legacy `effect_id`.
- Activate an allowlist of three to four simple out-of-combat uses through the
  existing reservation/replay boundary plus the explicitly accepted typed
  extension, if any.
- Materialize truthful `consumable`/`one-use` metadata and `Разові` visibility.
- Existing stacks become usable only through an explicit content decision and
  versioned tests.
- Consume exactly one stack unit after the action commits.

## Non-goals

- Take-away purchase shelf; that is `0.4.9`.
- Combat initiative/crit/party/raid effects, broad generated-effect inference,
  food buffs, hidden procs, item instances, market or crafting.

## Acceptance criteria

1. Only the reviewed allowlist appears as usable; flavor-only/unknown legacy
   stacks remain truthful and inert.
2. Preview/confirm rechecks current life, quantity, equipment, all destructive
   reservations, effective maxima and content fingerprint.
3. Duplicate/stale/concurrent use consumes one unit and applies one effect at
   most once; a failed/full-resource attempt consumes nothing.
4. Gift, mail, chest, barter, upgrade, altar, resale and group-action guards use
   the same tested destructive-inventory eligibility contract where applicable.
5. No item instances are introduced: identity is `itemId + quantity + content
   fingerprint`, and an equipped item id protects its whole stack.
6. Existing medical items and combat item actions remain regression-covered.

## Relevant files / search terms

- `ItemUseOrder`, item-use domain/repository result types, item content and
  materialization, `Разові`, inventory callbacks/presenters, resources/statuses,
  remort and all destructive inventory reservations.

## Focused tests

- Accepted/rejected catalog materialization including pre-existing stacks.
- Typed effect/result/presenter/remort tests for any one approved new family.
- Duplicate, stale, full-resource, quantity/equipment/fingerprint and
  cross-reservation races; existing medical/combat-item regressions.

## Manual Telegram QA

Prepare accepted, rejected and legacy stacks. Inspect `Разові`, use/replay each
accepted item, change quantity/equipment/reservation/remort before confirm and
verify rejected flavor items never advertise an unsupported use.

## Release surfaces

- Version/changelog/news, task plus accepted catalog, item-use architecture,
  content/balance/QA, achievement/Lore decision, ledger and AI context.
