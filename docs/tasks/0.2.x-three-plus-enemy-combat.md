# Future Task — Three-or-More Enemy Solo Combat

## Goal

Extend the shipped one-/two-enemy combat foundation so one adventurer can enter a bounded solo encounter against three or more monsters. This is the next priority combat expansion before broad party-help or real-raid work.

The first implementation must support at least three living enemy records. A higher cap may be enabled only as an explicit, balance-tested configuration; the task must not create an unbounded enemy list.

This is one player fighting a larger monster encounter. It is separate from the future player-help task, where two or three players share one fight.

## Scope

- Preserve the backward-compatible `monster` mirror for legacy one-enemy state while storing deterministic, ordered enemy records for 3+ encounters.
- Define stable primary/target selection and a compact Telegram target flow. Every eligible target must remain reachable; no silent keyboard truncation.
- Let attacks, class/race abilities, item actions and monster responses resolve against the selected living target according to their existing action contracts.
- Finish only after all encounter enemies are defeated; defeat/flee/timeout and stale callbacks must remain replay-safe.
- Keep one encounter reward settlement. Additional monsters must not automatically multiply XP, gold, loot or achievement progress.
- Keep the first slice PvE and bounded: no party participants, group chat, positioning grid or broad area-effect system.
- Reuse the shared combat journal/result path so the live card, stored replay and Chronicles summary name the relevant enemies without dropping the encounter when the third target is present.

## Non-goals

- no player-help or party combat;
- no full Big Barrel or real raid engine;
- no unbounded enemy count or arbitrary encounter builder;
- no summoner/backup trait rollout in this slice;
- no aggro table, tank/healer roles or tactical grid;
- no automatic per-enemy reward or loot multiplication;
- no hidden `slice(0, n)` target list that makes an eligible monster unreachable.

## Acceptance criteria

- Existing one- and two-enemy sessions, rewards and replays remain compatible.
- A deterministic 3+ enemy encounter serializes, loads and resolves all enemy states in order.
- Target selection reaches every living enemy and rejects defeated, foreign, stale or replayed target callbacks without mutating the fight.
- A fight cannot settle while any encounter enemy is alive, and it settles exactly once after the final enemy is defeated.
- Monster turns, class/race abilities, item actions, flee and timeout have focused regressions for a 3+ enemy state.
- Live combat, stored journals and Chronicles preserve the encounter subject/result when three or more enemies participate.
- Balance simulation covers incoming pressure, fight length and reward value before enabling a production encounter source.
- The task includes a narrow local/manual QA helper for any new target-selection gate or timer, without exposing dev helpers in production.

## Focused tests

- domain reducer/state tests for 1, 2, 3 and configured upper-cap enemies;
- target keyboard/callback tests proving every eligible target is reachable and stale callbacks are harmless;
- action tests for attacks, skills, items, monster turns, flee, timeout, defeat and final settlement;
- journal/replay/Chronicles presenter tests for all enemy names and terminal results;
- reward idempotency and legacy one-/two-enemy regression tests;
- deterministic balance simulation for encounter pressure and fight length.

## Manual Telegram QA

- Start a controlled 3-enemy fight and select each living target in turn.
- Defeat enemies in different orders, reload the fight between turns and replay stale target callbacks.
- Exercise a class/race ability, a combat item, flee, timeout and the final-enemy victory path.
- Confirm the live card, stored journal and Chronicles row retain all relevant encounter information.
- Confirm production configuration exposes no dev-only encounter or target helper.
