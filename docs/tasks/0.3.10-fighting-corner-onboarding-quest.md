# 0.3.10 — Fighting Corner Onboarding Quest

## Goal

Add a once-per-remort-life level 3+ quest, `Перше правило Бійцівського кутка`, that introduces the existing Fighting Corner through one Doppelganger training fight, one quick duel and one turn-based duel, then sends the player back to the Quest Table for a replay-safe level-scaled reward.

## Scope

- Add one explicitly accepted current-remort-life quest over the existing training, quick-duel and turn-based-duel flows.
- Record the three objectives as best-effort, idempotent follow-ups without changing combat, duel or tournament settlement.
- Add Quest Hub, quest-overview, Fighting Corner and quest-marker states plus one replay-safe Quest Table reward claim.
- Add focused automated coverage, a production-safe local reset helper and the release/manual-QA surfaces listed below.

## Product decisions

- Minimum level: 3, matching the existing Fighting Corner, training and duel gates.
- No maximum level or retirement gate.
- The quest is available once in each remort life.
- A remort starts a fresh quest life; progress and rewards from the previous life must not carry over.
- The quest must be explicitly accepted at `Стіл зі справами`.
- Acceptance stores a millisecond-precision `acceptedAt`; only durable objectives with `occurredAt > acceptedAt` count. Events before or exactly at acceptance do not count.
- The three objectives may be completed in any order after acceptance.
- Winning is not required.
- Reward claiming requires all three objectives and current normalized presence at the Quest Table.
- Ship quest availability, markers and claiming behind an explicit production-off rollout flag until target-runtime verification is accepted.
- Review the existing Fighting Corner entry in `📖 Перекази`; no lore change is expected for an onboarding wrapper over shipped modes, but the implementation PR must record that decision or update the entry if shipped behavior contradicts it.

## Player flow

1. A level 3+ character sees `Перше правило Бійцівського кутка` at the Quest Table.
2. The character accepts it.
3. The quest card explains:
   - how to reach `🥊 Бійцівський куток`;
   - that duel invite cards/links can be forwarded to another player;
   - that `👀 Хто поруч` → `Кинути виклик присутнім` can find a nearby opponent;
   - that both quick and turn-based modes require the other player’s consent.
4. The player completes:
   - one valid Doppelganger training session;
   - one resolved ordinary quick duel;
   - one valid terminal turn-based duel with at least one resolved round.
5. Each newly completed objective produces a short best-effort progress notification.
6. At `3/3`, the player is told to return to the Quest Table.
7. The Quest Table grants the stored reward exactly once.
8. The completed quest appears in the current-life archive and becomes available again only after remort and reaching level 3.

## Progress rules

### Doppelganger training

Count a terminal completed training session after quest acceptance regardless of victory or defeat.

Do not count flee, expiry, cancellation, stale replay or an active session.

### Quick duel

Count a normally resolved `quick` duel for each eligible participant who has accepted the quest in the current life.

Do not count declined, cancelled, expired or stale challenges, Rogue retaliation/system quick duels, or mere invite creation.

### Turn-based duel

Count a terminal turn-based duel for each eligible participant only if at least one combat round was resolved.

A win, loss or draw may count. A zero-round cancellation, expiry or immediate non-combat walkover must not count.

Progress recording must be idempotent and must never alter the normal duel result, XP, tournament scoring or rewards.

## Persistence and concurrency

- Reuse the established `DailyAction` current-life pattern used by `BarrelBeerTutorialService` and `FirstKorchmaQuestService`.
- Use the canonical remort-life token as `localDate`.
- Use separate stable keys for acceptance, each objective and completion.
- Pass `expectedLife.remortCount` for every mutation.
- Do not add a Prisma model or migration unless repository inspection proves the existing current-life ledger cannot represent the feature.
- Read all quest keys through one bounded query rather than one query per objective.
- Duel/training completion remains the primary transaction. Quest progress and Telegram notifications are best-effort follow-ups and must not roll back combat.
- Duplicate callbacks, terminal recovery and concurrent reward claims must replay stored state without duplicate progress, XP, gold or items.

## Reward

Calculate at first successful Quest Table claim:

- XP:
  - use the remort-adjusted width of the character’s current level;
  - for max level, use the last finite level-band width;
  - `min(42, max(5, ceil(levelBandWidth * 0.42)))`.
- Gold:
  - `min(93, 13 + characterLevel * 6)`.
- Items:
  - one capped starter tool, `item.pink-soap-of-first-rule`, through `starterEquipmentGrant(...)`; while that exact base item is owned it is neither duplicated nor listed as applied, but a later remort-life claim may grant it again if the base item is no longer present;
  - guaranteed `1 × item.iskrokamin`;
  - also enable the existing canonical `questIskrokaminBonus` for eligible level 4+ quest claims.

Persist the exact XP, gold and applied item grants. Replayed claims must display the stored reward instead of recalculating or rerolling it.

The underlying training and duel modes keep their existing independent rewards and tournament behavior.

## Quest markers and navigation

- Available quest: `⚠️` at the Quest Table.
- Accepted but incomplete: `⚠️` on the Fighting Corner route.
- Ready to claim: `✅` on the Quest Table route and a clear return button from the Fighting Corner.
- Add the quest to:
  - Quest Hub active rows;
  - `🗺️ Квести` overview while active or claimable;
  - current-life Quest Hub archive after completion;
  - Fighting Corner progress presentation.
- Do not add a direct claim outside the physical Quest Table.
- Do not undo the `0.3.9` quest-marker fan-out reduction. Fold the new state into an existing bounded DailyAction snapshot/source where practical.

## Non-goals

- No new duel mode.
- No duel matchmaking service.
- No changes to tournament scoring or prizes.
- No wagers, item loss or PvP injuries.
- No repeatable pre-remort farming.
- No retroactive credit for old fights.
- No public shame or mandatory victory.
- No new achievement or cosmetic title: the quest onboards existing visible actions, while its own progress and current-life archive already provide the new milestone surface.
- No broad quest-engine rewrite.
- No unrelated combat or economy rebalance.

It must not be registered or callable in production and must not remove historical previous-life rows. Cover production configuration explicitly, including when the feature-specific dev-helper flag is set, and document the helper in developer setup, compact context and the implementation PR body.

## Acceptance criteria

- Level 1–2 characters cannot accept the quest.
- A level 3+ character can accept it in every remort life.
- High-level characters can still take it if they skipped it earlier.
- Pre-acceptance fights do not count.
- Each valid objective is recorded once.
- Objectives work in any order.
- Both duel participants can receive their own progress independently.
- Invalid/unfinished terminal states do not count.
- `3/3` does not auto-pay the reward.
- Claim outside the Quest Table fails without mutation.
- First valid claim grants the calculated reward once.
- Duplicate and concurrent claims replay the same stored reward.
- Remort hides the previous life’s progress, locks the fresh quest until level 3 and then offers it again.
- Quest progress failures or Telegram delivery failures cannot roll back combat.
- Quest markers point to the Fighting Corner while progressing and the Quest Table when ready.
- Existing training, quick-duel, turn-based-duel and tournament behavior remains unchanged.

## Manual Telegram QA

Use two ordinary player accounts:

1. Reach level 3 and accept the quest at the Quest Table.
2. Confirm the Fighting Corner route receives the active marker.
3. Finish the three objectives in different orders across the two accounts; include a lazily settled expired Doppelganger turn through `/spar`, the mode callback and the battle journal.
4. Create one duel through a forwardable link.
5. Create the other through `Хто поруч`.
6. Lose at least one valid activity and confirm it still counts.
7. Verify each progress notification and the `3/3` return direction.
8. Attempt claim away from the Quest Table.
9. Claim at level 3 and record exact XP, gold, the pink-soap tool and one Iskrokamin; repeat at level 4+ and verify the guaranteed stone plus the exact stored canonical bonus result. The focused two-stone assertion uses a controlled deterministic fixture and is not a universal level 4+ promise.
10. Replay the claim and verify no duplicate reward.
11. Repeat with the soap already owned: it must be omitted from the applied/replayed reward while the quest still completes.
12. Remort and verify old progress does not carry. At level 3 the quest must return; a still-owned exact base soap stays capped at one, while an absent base soap may be granted again without implying upgrade-family ownership.
13. Run the local reset helper and repeat the current-life flow.
14. With `FIGHTING_CORNER_ONBOARDING_QUEST_ENABLED=false`, verify no quest rows/markers/notices appear and ordinary duel replay remains unchanged.

## Implementation record

- Implemented without a Prisma schema change or migration. Five stable current-life `DailyAction` keys cover acceptance, the three objectives and completion; all five are loaded by one bounded `key IN (...)` read.
- Acceptance stores an authoritative millisecond timestamp. Objective hooks require a strictly later durable occurrence, so before/equal timestamps fail closed without relying on coarse `DailyAction.createdAt`.
- Every terminal Doppelganger path, including lazy `/spar`, mode-callback, player turn, first view, first battle-journal recovery and scheduled timeout, propagates the canonical post-settlement session and runs the same idempotent quest hook before non-essential delivery. Quick Rogue retaliation is excluded by its persisted invite token relation; enabled turn-based credit uses one bounded `findFirst`-style existence query for `round`/`timeout-attack`, while the disabled feature performs zero quest-specific journal reads.
- Combat/duel settlement commits first. Idempotent quest progress and Telegram notification delivery are contained best-effort follow-ups, including terminal replay recovery for missed progress.
- The exact claim reward stores only actually applied grants after each grant's own cap semantics, then coalesces equal item ids so guaranteed and bonus Iskrokamin appear as one summed row. Replay normalizes older duplicate applied rows. The starter soap cap covers the exact base item only while owned; current-life keys plus `expectedLife.remortCount` isolate remorts and concurrent claims.
- The marker still reports eight grouped primary sources, which is source attribution rather than literal SQL count. When enabled, Fighting Corner adds one bounded five-key `DailyAction` query inside the grouped Fight source; disabled duel settlement adds zero quest queries. Quest Hub now reuses that grouped Fight snapshot instead of separately repeating Fight/problem/Fighting Corner character and quest reads.
- Production availability remains off by default. `/dev_reset_fighting_corner_quest` is non-production only and deletes only the current-life five-key set when its local helper flag is enabled.
- Achievement decision: deliberately none, as approved in Non-goals; the quest wraps already shipped visible actions and supplies its own current-life milestone/archive surface.
- Lore review: the existing `Бійцівський куток` entry already truthfully distinguishes training from duels, so no lore copy change is needed.
