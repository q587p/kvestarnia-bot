# 0.3.9 — Quest Marker Snapshot DB Fan-out Reduction

## Goal

Reduce the measured database-dominated latency of `main-menu.quest-markers` by removing repeated Adventure and Fight reads while preserving every existing quest-marker state, route, keyboard and fail-soft result.

## Evidence

The prior sanitized 0.3.8 summary states that a combined dataset contained 506 complete records and that `main-menu.quest-markers` had `N=224`, a `47.3%` slow rate, `341 ms` p50, `626.9 ms` p95 and `37.8%` of measured total latency, with recorded time described as effectively all `dbMs`. The current snapshot starts up to ten optional service lookups in one primary `Promise.all`. `fight.turn` is separately slow and remains a documented follow-up rather than part of this release.

### Controlled-evidence provenance status

The aggregate values above are retained as planning context, not as a verified controlled baseline. The sanitized source artifact and extraction manifest are not present in the repository or PR, so the following required provenance cannot be reconstructed without guessing:

- deployed 0.3.8 commit SHA or SHA set (the PR base SHA is not proof of deployment);
- non-secret Render instance scope used by the export;
- exact inclusive/exclusive UTC window and its corresponding Kyiv-local window;
- effective `sampleRate` and `thresholdMs` for every included record;
- coverage of `random-sample`, `slow-tail` and `terminal-error` evidence kinds;
- rules for combining exports, deduplicating overlaps, and including or excluding incomplete/error records;
- the complete 506-record denominator composition and the route-level denominator definition behind `N=224`;
- the exact slow numerator and denominator behind the rounded `47.3%` claim;
- the precise population used for p50/p95 (all complete calls, successful calls, slow-tail calls, or another subset);
- the method and all-route population used to calculate the `37.8%` measured-latency share and the claim that latency was effectively all database time.

Exact blocker: recover a sanitized aggregate manifest from the evidence owner, or rerun a controlled 0.3.8 measurement with the fields below. Raw production logs, player identifiers, SQL data and private values must not be committed or pasted. Until that blocker is cleared, the numerical baseline and any claimed improvement against it remain unproven.

### Like-for-like 0.3.9 comparison contract

No deployment is part of this task, so the absolute post-deploy window cannot be recorded yet. The comparison window is defined as `[T0, T1)`, where `T0` is the first accepted record after the final 0.3.9 commit is observed in `renderGitCommit` on the approved non-secret Render instance scope, and `T1 - T0` exactly matches the recovered 0.3.8 baseline duration and Kyiv day-of-week/time-of-day coverage. If the baseline manifest cannot be recovered, a new 0.3.9 window may be reported only as a standalone measurement, not as a like-for-like improvement.

The sanitized comparison manifest must record:

- final deployed commit SHA(s), non-secret instance scope, and exact `[T0, T1)` in UTC and Kyiv time;
- `route`, platform timestamp, `renderGitCommit`, `renderInstanceId`, `evidenceKind`, effective `sampleRate`, `thresholdMs`, `outcome`, `errorCategory`, `errorComponent`, `resultState` and `rowCount`;
- `totalMs`, `dbMs`, `computeMs`, `telegramMs`, `questMarkerSourceCount`, `questMarkerSlowestSource` and `questMarkerSlowestSourceMs`;
- the same route filters, instance scope, evidence-kind coverage, inclusion/exclusion rules and deduplication key as the recovered baseline; overlapping exports must be deduplicated by one stable platform event id before combination;
- exact total, successful, error and slow numerators/denominators. An unweighted complete slow rate is valid only for a fully observed interval (effective sample rate `1`); otherwise the sampling-weight method and uncertainty must be stated instead of treating emitted records as a complete denominator;
- p50/p95 over the explicitly named successful `totalMs` population, plus measured-latency share as `sum(main-menu.quest-markers totalMs) / sum(all included route totalMs)` over the identical window and evidence population.

`questMarkerSlowestSourceMs` is overlapping high-level source wall-clock latency. Sources run concurrently, so it is neither exclusive SQL time nor additive with sibling source durations.

## Scope

- Add shared Adventure and Fight quest-marker snapshot methods that retain the existing source-specific result types.
- Reuse one Adventure character/equipment read for the regular and starter Adventure markers.
- Reuse one Fight character read for the fight-overview and problem-quest markers.
- Prefer the grouped methods from the main-menu snapshot, reducing its primary service-source fan-out from ten to eight; keep the existing legacy fallback for compatible test/adaptor implementations.
- Preserve per-result fail-soft handling with settled grouped results, and use one bounded error-only fallback to independent child lookups when a grouped shared root fails, so recoverable siblings and unrelated markers survive without retrying ordinary rejected children.
- Emit only bounded `questMarkerSourceCount`, allowlisted `questMarkerSlowestSource` and timing attribution on the existing privacy-safe performance record.
- Add focused marker-state, fail-soft, source-call and repository-read count coverage.

## Non-goals

- No cache, speculative precomputation, broad quest rewrite, schema, migration, dependency, reward, balance, timer, cooldown, route, keyboard or player-visible behavior change.
- No raw production log, SQL parameter, player state, Telegram id or dynamic source label.
- No `fight.turn` optimization; its DB/Telegram critical path is a separate measured follow-up.
- No achievement: the release adds no visible action, milestone or gameplay outcome.
- No lore or quest-overview update: the in-world behavior, quest states and guidance are unchanged.
- No rollout flag: the read reduction preserves the existing output contract and has direct fallback coverage.
- No `/dev_*` helper: the release adds no runtime gate, timer, random offer, pending session, retry or mutation to accelerate.

## Acceptance criteria

- The production snapshot uses one grouped Adventure source and one grouped Fight source instead of four independent top-level sources.
- Adventure performs one fewer character read and one fewer equipment read than the equivalent separate marker calls; Fight performs one fewer character read.
- A rejected grouped sub-result still preserves its successful sibling and all unrelated marker sources.
- A rejected grouped shared root invokes the legacy independent children once; there are no unbounded retries and ordinary rejected child results are not retried.
- Adventure period and Mimic local-date inputs are captured before shared character/equipment awaits.
- Existing marker states, optional no-character behavior, route guidance and keyboard labels remain unchanged.
- Performance payloads expose the actual bounded source count and one runtime-allowlisted slowest-source label with finite, non-negative, bounded timing and no raw data.
- Focused tests and `npm run check` pass.
