# 0.4.10 — Nearby Greeting Buff

Status: proposed, blocked on one explicit effect/stacking decision.

## Goal

Add a warm opt-in `👋 Привітатися` action in `Хто поруч` that gives one nearby
adventurer a tiny, bounded support status without creating a mandatory pre-fight
rotation or replacing Priest, Bard, Varenyk-mancer or Shynok support.

Source draft: `docs/tasks/archive/0.2.x-nearby-greeting-buff.md`.

## Activation decision

Choose exactly one effect before runtime work. The old draft lists recovery,
next-fight morale, reward bonus and luck-like alternatives; they are not one
combined scope. Prefer an out-of-combat recovery-only status, no direct XP/gold
faucet and strongest-only/non-stacking interaction with Shynok recovery.

The activated task must document:

- stacking/replacement against drink recovery, `😋 Ситий`, Inspiration and
  Priest blessing;
- wall-clock behavior while combat is active;
- which solo/training/duel/PartyBoss/GroupCombat settle/start/release paths read
  the effect;
- target-global active-status and actor-target repeat-wait policy.

## Scope

- Existing exact-normalized same-location presence and active cutoff.
- Actor chooses one non-self target, previews and confirms through a short
  server-owned token.
- One target status, one activation receipt and one actor-target `93`-minute
  repeat wait, committed atomically and replay-safe. Receipt/status/wait carry
  actor and target current-life identity rather than a bare Telegram id.
- One private target notification only after a fresh durable success.
- Truthful status/wait display and stale/no-longer-nearby/busy handling.

## Non-goals

- Relationship graph, friendship/guild requirement, public feed pressure,
  stacking greeting parties, item/gold transfer or direct reward multiplier.
- New class ability family or changes to existing support abilities.

## Acceptance criteria

1. The task and balance docs name one exact effect and a complete stacking/time
   policy before implementation begins.
2. Duplicate/replayed/stale confirms cannot duplicate status, cooldown,
   achievement event or notification.
3. Same actor-target repeat wait and one active target status are race-safe.
   Remort of either side invalidates the old-life status/wait/callback even when
   the underlying generic cooldown table itself survives remort.
4. Every canonical resource/combat boundary named by the chosen effect is tested;
   unsupported paths cannot silently display an effect they ignore.
5. No self/remote/busy target mutation and no XP/gold/loot/quest faucet exists.
6. Two-account Telegram QA covers movement, active flows, duplicate callbacks,
   replacement/blocking and expiry.

## Relevant files / search terms

- `nearbyDuel`/`Хто поруч`, presence service, class-noncombat cooldown/status
  repository, Shynok recovery, Sated/Inspiration/Priest status presenters,
  remort cleanup and canonical resource settle/start/release paths.

## Focused tests

- Callback token parser and activation receipt replay.
- Same-pair/global-target concurrent confirms, move/busy/remort races and one
  notification invariant.
- Table-driven stacking/time behavior on every path required by the chosen effect.

## Manual Telegram QA

Use two to three same-location accounts. Greet, replay, move/remort the target,
enter a blocking flow, try a second greeter, cross expiry/wait and inspect all
visible status/recovery surfaces.
