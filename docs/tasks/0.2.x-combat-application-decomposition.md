# 0.2.x — Combat Application Decomposition

Draft conditional follow-up. Assign the next free `0.2.x` version only after reviewing the `0.2.1` multi-enemy result and the `0.2.2` architecture closeout.

## Goal

Keep `FightService` as a stable facade for bot commands, Yeger integration and schedulers while moving distinct combat application workflows behind focused collaborators.

Make ordinary fight start, turn, timeout, settlement, rewards and problem-quest behavior independently reviewable before further threat/party complexity.

## Trigger

Schedule this task before Threat Escalation only if the release-sequence gate in `docs/architecture/0.2.x-release-sequence.md` fires.

Otherwise keep it as later `0.2.x` maintenance.

## Scope

- Introduce a named `FightServiceDependencies` object or equivalent factory-level dependency object.
- Preserve the public methods consumed by the bot and other services.
- Extract focused internal collaborators, adjusted to the actual post-multi-enemy code:
  - encounter/preview coordinator;
  - active session and turn coordinator;
  - timeout coordinator if it has independent state transitions;
  - terminal resource/reward settlement coordinator;
  - problem quest coordinator;
  - pure difficulty, encounter and reward policies.
- Move shared result contracts to a stable `services/fight/` contract module when this reduces import cycles.
- Keep Telegram presentation outside the service.
- Keep repository transactions and compare-and-set boundaries explicit.
- Add characterization tests before moving stateful logic.
- Preserve legacy stored combat rows and replay behavior.

## Placement rules

Use `src/domain/` only for pure game rules that:

- have no repository;
- have no clock or Telegram dependency;
- accept ordinary data;
- return deterministic ordinary data.

Use `src/services/fight/` for application workflows that:

- call repositories;
- coordinate clocks/RNG;
- own idempotency or settlement;
- combine several domain policies.

Do not move Prisma types into domain.

## Non-goals

- No Threat Escalation behavior.
- No new enemy-count progression.
- No reward rebalance.
- No new combat action.
- No schema/migration unless a separately approved compatibility blocker is proven.
- No rewrite of the pure combat engine.
- No replacement of existing repository interfaces.
- No event sourcing, CQRS framework or generic workflow engine.
- No bot modularization work already completed in `0.2.2`.
- No player-facing copy change.

## Acceptance criteria

- Existing `FightService` consumers require no behavior-level rewrite.
- Public result unions remain compatible or have a narrow documented import-only change.
- Start, turn, timeout and terminal settlement can be tested through focused collaborators.
- Exactly-once reward/resource settlement remains in a clearly owned transaction/CAS path.
- Replay, stale turn, zero-HP repair, expiry and remort-life behavior remain unchanged.
- Problem quest issue/progress/turn-in behavior remains unchanged.
- Yeger, adventure and ordinary Nyz sources reuse the same canonical session transition paths.
- Multi-enemy compatibility readers remain centralized.
- No repository-aware module is placed in `src/domain/`.
- No circular import is introduced.
- `FightService` becomes a facade/coordinator rather than the home of every policy.
- Full checks and manual combat regression pass.

A smaller file is expected, but line count is not the acceptance criterion. Ownership and test seams are.
