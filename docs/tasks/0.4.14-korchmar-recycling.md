# 0.4.14 — Korchmar Recycling

Status: proposed only after stable `0.4.13` resale evidence; not
implementation-ready until the neutral batch algorithm is frozen in this task.

## Goal

Recycle low-value units sold to Korchmar in bounded neutral five-unit batches and
put only qualifying outputs into the resale shelf.

## Scope

- Cheap eligible sold units enter a Korchmar-owned recycling pool in the same
  transaction as sale consumption/payout, with one unique source-sale/line
  intake receipt.
- A neutral deterministic batch owns a unique id, rules version, ordered frozen
  input units/fingerprints, deterministic seed, persisted outcome and status.
  A completed batch consumes exactly five pool units and creates one output.
- Output with canonical `goldValue >= 93` enters `0.4.13` resale stock; cheaper
  output may enter a later batch.
- Process at most one to three batches per triggering mutation; store a resumable
  cursor/result and leave remaining work for a later player-driven trigger.
- Separate domain/repository path from player-owned `MantokChestRun`.

## Activation gate

Amend this task with deterministic pool selection order, semantic fingerprint,
rules version, seed derivation, candidate/output algorithm, transaction owner,
trigger and exact per-trigger cap. Freeze a `blocked-no-candidate` outcome: its
five inputs remain reserved and unconsumed, it creates no output, never retries
automatically, and requires explicit repair after content/rules correction.
Codex must not invent these economy rules while writing the schema/repository.

## Non-goals

- Background scheduler, unbounded loop, character LUCK, player achievements,
  seller rewards, crafting, item instances or market pricing.

## Acceptance criteria

1. Each completed batch consumes five pool units and creates exactly one output
   once under retry/restart/concurrency; source-sale intake is also exact-once.
2. Batch generation is neutral: no character stats, achievements, quests or
   private player ownership leak into the result.
3. Per-trigger limits prevent an infinite cheap-output cycle; repair/resume does
   not repeat a completed batch.
4. Resale threshold/fingerprint/quarantine behavior is identical to `0.4.13`.
5. Existing Friendly Chest and seller payout remain unchanged.
6. Property tests cover long cheap-output chains, exact 5-consumed/1-created
   accounting, blocked-no-candidate inputs and bounded work; rollout has economy
   monitoring and a kill switch.

## Relevant files / search terms

- `0.4.13` resale stock, Shynok sale transaction/source receipt, Friendly Chest
  generation domain (reference only), semantic fingerprint/value, repair/flags.

## Focused tests

- Deterministic selection/seed/output golden cases and rules/content drift.
- Sale+pool-intake atomicity, five-to-one accounting, concurrent trigger/restart/
  repair exact-once and 1–3-batch work bound.
- Blocked-no-candidate and long cheap-output property simulations; prove no
  player LUCK/achievement/private-ownership effects.

## Manual Telegram QA

Seed a local neutral pool, trigger zero/one/multiple bounded batches, force a
no-candidate block, restart/repair midway, inspect resale output, toggle the flag
and verify no player reward/achievement or Friendly Chest mutation.

## Release surfaces

- Version/changelog/news, task with frozen algorithm, balance/simulation/QA,
  operations/repair/rollback, achievement/Lore decision, ledger and AI context.
