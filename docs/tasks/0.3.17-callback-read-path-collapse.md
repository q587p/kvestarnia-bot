# 0.3.17 — Callback Read-Path Collapse

## Goal

Reduce common Telegram callback latency by collapsing the source-proven Friday pending-raid and quest-marker SQL waterfalls, reusing mutable read results only within one update, and measuring the entire middleware-to-first-response path.

This is a semantics-preserving performance release. It does not introduce concurrent update polling, a database migration, a new cache tier or gameplay changes.

## Base gate

Start from current `origin/main` only after the required 0.3.16 runtime content from PR #182 is present. The audited PR head was `bd0bc03c8794c2fc7dadc4fcf53de5a26138499d`, but a squash merge may produce a different main SHA.

If the required content is absent or PR #182 remains the only branch containing it, stop and report the blocker. Do not stack 0.3.17 on the open 0.3.16 branch unless the owner explicitly requests a stacked PR.

Do not duplicate or revert PR #182's Big Barrel terminal fan-out, accepted raid-chat background delivery, bounded raid-chat Telegram gate, 42-second maintenance split or PartyBoss bounded-history changes.

## Evidence

### Friday pending guard

`TavernRaidService.findRelevantPendingFridayBarrelRaid()` resolves Character and then awaits 24 period candidates. Each `CooldownRepository.findForTelegramUser()` resolves Character again and reads one cooldown; a found cooldown also calls `DailyActionRepository.findForTelegramUser()`, which resolves Character again and reads one action.

Static cost before route work:

- no pending rows: `1 + 24 × 2 = 49` SQL statements;
- historical cooldown plus completed action for every candidate: `1 + 24 × 4 = 97`;
- global middleware, a local handler guard and Daily Korchma/marker paths can repeat the same lookup 2–3 times per update.

Relevant files:

- `src/services/tavernRaidService.ts`
- `src/db/repositories/prismaCooldownRepository.ts`
- `src/db/repositories/prismaDailyActionRepository.ts`
- `src/bot/middleware/registerCombatLockMiddleware.ts`
- `src/bot/middleware/pendingRaidGuard.ts`
- `src/bot/commands/pendingRaidGuard.ts`
- `src/services/dailyKorchmaRoundService.ts`

Existing unique indexes already support exact batch reads:

- `CharacterCooldown(characterId,key)`;
- `DailyAction(characterId,key,localDate)`.

No migration is required for this slice.

### Quest markers

`questMarkerSourceCount` reports logical services, not SQL statements. The grouped Fight source still recalculates overlapping problem-quest state and repeatedly resolves Character/ledger rows. A seeded source expansion is roughly 48–50 SQL statements before other marker sources.

Relevant files:

- `src/bot/questMarkerSnapshot.ts`
- `src/services/fightService.ts`
- `src/db/repositories/prismaDailyActionRepository.ts`
- `src/db/repositories/prismaSoloCombatSessionRepository.ts`
- `src/services/dailyKorchmaRoundService.ts`

The existing bounded raw-SQL pattern in `countProgressEligibleWinsByTelegramUserId` should be reused or extended instead of loading unbounded combat history.

### Observability gap

Existing route spans start inside handlers, after pending/combat/presence middleware. Historical 0.3.11 evidence recorded `fight.turn` N=80, p50 705.2 ms, p95 1874.0 ms, mean DB 388.4 ms and mean Telegram 407.0 ms, but these figures are not a live 0.3.16 baseline and omit most current pre-route work.

## Scope

### 1. Bounded Friday pending snapshot

- Resolve Character once.
- Build and deduplicate the 24 exact candidate period ids/keys.
- Read all matching CharacterCooldown rows in one bounded `IN` query.
- Read all matching completed Friday DailyAction rows in one bounded `IN` query with `take` no larger than the candidate count.
- Resolve the newest relevant pending period in memory while preserving current candidate order and boundary behavior.
- Do not `await` inside the candidate-selection loop.
- Preserve current `no-character`, `none`, `pending`, current/older period, audit-break, completion and remort/life behavior.
- Keep a fresh late recheck only where an authoritative mutation requires it for race safety.

Prefer a purpose-built read snapshot or narrow repository APIs such as:

- `listForCharacterByKeys(characterId, keys)`;
- `listForCharacterByLocalDates(characterId, { key, localDates, take })`.

Do not make the general Telegram-user repositories silently cache mutable state.

### 2. One request-local activity read per update

- Introduce a narrow request-scoped memo/single-flight seam for the pending Friday result.
- Reuse the same in-flight Promise/result across global middleware, handler-local guard, Daily Korchma context and quest-marker lookup in one grammY update.
- Reuse an already-started full Fight overview between combat-lock preflight and a marker consumer when both genuinely need the identical pre-mutation view.
- Keep the memo request-local. No process-wide TTL cache, stale cross-update result or mutable global player snapshot.
- A mutation that can change pending/combat state must invalidate/bypass the pre-mutation view before a required late authoritative decision.
- Preserve all current guard precedence, callback-source repair and race-safe mutation checks.

### 3. Collapse and avoid quest-marker reads

- Add a shared marker DB snapshot that resolves Character once and batches the exact DailyAction keys needed by current marker consumers.
- Calculate Thirteen Small Problems progress once and share it between Fight overview/problem marker branches.
- Reuse bounded combat-progress primitives; do not materialize full win history to answer a threshold no higher than 93.
- Keep each source fail-soft without retrying successful siblings or converting one failure into an unbounded fallback.
- Branch before building quest markers. Do not build them for Shynok static rules/local submenus, Hero, Quest Table, News Corner, Fighting Corner, Deep/fight-preview or other routes that do not render marker-aware navigation.
- Replace the unconditional full Daily Korchma context on every location click with a cheap bounded exact-location pending-scene check; keep full context authoritative for actual DKR scene/action/claim flows.
- Remove the Hero main-menu quest-marker keyboard build that is discarded by the existing inline Hero keyboard.
- For a mutation that changes marker state, use one lazy memo and one explicit post-mutation invalidation/reload; do not build both pre- and post-mutation snapshots without a consumer.

### 4. End-to-end callback telemetry

- Start a privacy-safe trace before combat-lock and presence middleware.
- End it at handler completion or terminal error.
- Observe the first `answerCallbackQuery` and the first presentation method (`editMessageText`, `sendMessage` or equivalent) through the existing Telegram API transformer seam or another concurrency-safe request context.
- Emit bounded, allowlisted fields only:
  - route namespace/kind, never raw callback data;
  - `preRouteMs`;
  - `pendingRaidMs` when run;
  - `combatLockMs` when run;
  - `presenceMs` when run;
  - `ackMs` when observed;
  - `firstPresentationMs` and method class when observed;
  - `totalMs`;
  - terminal outcome/error component from an allowlist.
- Keep the existing disabled-by-default random sampling and always-on slow/error behavior.
- Never emit Telegram/user/chat/message ids, callback payload/token, player state, SQL text/parameters, URLs, error messages or stack traces.
- Do not label Telegram update age as exclusive bot queue time.

Actual SQL statement budgets belong in isolated integration tests using Prisma query events. Do not emit SQL text in production telemetry.

## Acceptance criteria

### SQL budgets

- Friday no-character path: no more than 1 SQL statement.
- Friday no-pending, current pending, older pending and completed-history paths: no more than 3 SQL statements each, independent of 24 candidates.
- No candidate-period loop contains an awaited repository call.
- One integration callback update performs exactly one pre-mutation Friday lookup; handler/DKR/marker reuse causes zero additional Friday SQL.
- Grouped Fight/problem marker source performs no more than 5 SQL statements in representative no-character, new-character and veteran fixtures.
- The complete main-menu marker snapshot performs no more than 12 SQL statements in the representative full-source fixture.
- A fixture with 10,000 irrelevant combat/DailyAction rows does not increase query count; bounded combat candidate/result count remains at or below the explicit hard cap and no higher than 93 valid rows are required.

Use actual Prisma `query` events, following the existing pattern in `tests/db/prismaHpRecoveryNotificationRepository.integration.test.ts`. Mocked repository-method counts are useful but do not satisfy these SQL budgets.

### Route behavior

- Shynok `game-dice-poker-rules` performs zero quest-marker builds and acknowledges before route-optional reads; it renders the identical rules/card/keyboard.
- Hero performs zero quest-marker builds and renders the identical inline Hero keyboard.
- Quest Table, News Corner, Fighting Corner, Deep and fight-preview location routes perform zero unused marker builds.
- A marker-bearing update invokes a full Fight overview at most once.
- Pending Friday, active duel, active PartyBoss, active solo/training fight, passage and stale/terminal callback behavior remains unchanged.
- Current DKR exact-location scene opening and post-mutation marker updates remain correct.

### Telemetry and safety

- Top-level trace includes global middleware time and records first ack/presentation once.
- Success and terminal failure emit at most one record per traced update.
- All numeric values are finite, non-negative and bounded.
- Privacy tests reject ids, raw callback data, tokens, SQL, URLs, player values, raw messages and stacks.
- No new dependency or migration appears in the diff.
- Focused tests, `npm run check` and `git diff --check origin/main...HEAD` pass.
