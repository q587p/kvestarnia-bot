# 0.4.0 — Party vs Many Proof

Status: repository implementation complete for `0.4.0`; deployment,
production availability and manual Telegram QA remain unproven.

Architecture: `docs/architecture/party-combat-evolution-plan.md`
Design: `docs/design/guilds-and-party-progression.md`

## Goal

Prove a separate, reusable and restart-safe 2–3 player versus 2–3 enemy combat
runtime through one feature-flagged non-production encounter with no economy.

## Scope

- Reuse an existing eligible `PartySession` roster.
- Add `GroupCombatSession`, `GroupCombatParticipant` and `GroupCombatAction`
  persistence plus safe migration/indexes.
- One strict versioned state/result schema and parser/repair path.
- One authored deterministic 2–3×2–3 encounter behind default-off and
  non-production/dev entry points.
- Freeze same-life actor/equipment/resource snapshots atomically with leases.
- One explicit self/ally/enemy target action per living participant per turn.
- Unique actor/turn queue, optimistic version CAS, deterministic resolver and
  server-owned timeout fallback.
- One canonical private participant card with edit/repair convergence.
- Bounded recap and contribution counters, but no settlement rewards.
- Central typed combat-lease owner/repair registry including the new kind.
- Unit/integration/race/load tests, simulation seed and docs.

## Non-goals

- Production rollout, XP, gold, items, quest progress or achievements.
- Guild schema or UI.
- Big Barrel migration or behavior/copy/balance changes.
- Full parity for every ability/item; unsupported actions are hidden with an
  explicit inventory and follow-up contract for `0.4.1`.
- >3 players, >3 enemies, public matchmaking, raid finder or group chat.
- Broad solo/duel/FightService refactor.

## Acceptance criteria

1. Two and three eligible joined participants can start the dev encounter with
   two and three enemies respectively; invalid party size/life/busy states fail
   without partial leases or rows.
2. Session/participant/action identities are relational and strict. Malformed or
   rules-mismatched state is CAS-invalidated without rewards; repair releases all
   recoverable locks and statuses.
3. An action names an allowed target and server revalidation rejects dead,
   missing, wrong-side and stale-turn targets without mutation.
4. Exactly one action per actor/turn persists. Last-action, duplicate,
   action-vs-timeout and concurrent scheduler races resolve at most once.
5. Resolver output is deterministic for stored state/actions/RNG seed and keeps
   stable actor/enemy order. Terminal rules cover victory, defeat and no living
   target without reviving a zero-HP actor.
6. Timeout fallback spends no item/scarce resource. Restart before/after action,
   resolution and delivery converges from DB state.
7. `/restart` and `/remort` are transactionally blocked for every participant.
   Leave/kick/leader changes cannot delete or mutate the active combat roster.
8. Each participant owns one canonical private card. Telegram edit/send failure
   never rolls back combat; later refresh repairs safely without message spam.
9. The proof writes no XP, gold, inventory, quest, achievement or ordinary
   activity reward. Terminal result is explicit `rewardless-proof`.
10. Due scans are lean, resolution loads current-turn actions only, recap/state/
    cards are bounded and a 3×3 25-turn load fixture stays within documented
    query/size budgets without flaky wall-clock assertions.
11. Existing solo, duel and PartyBoss tests/simulations are unchanged and green.
12. The flag defaults off; the dev route cannot register or mutate in production.

## Implemented contract

- The additive `GroupCombatSession`, `GroupCombatParticipant` and
  `GroupCombatAction` models keep stable roster/action identities. The session
  JSON owns enemies and the newest five recap rounds, so no unbounded round
  table or historical-action load is needed.
- `attack`, self `guard` and living-ally `aid` are the complete proof action
  inventory. A server timeout inserts only self guard and spends no mana, item
  or other scarce resource.
- Start atomically claims the recruiting `PartySession`, verifies the 2–3
  current-life roster and combat leases, then freezes resources, equipment,
  `Ситий` and `Натхнення` into participant snapshots. Any invalid size, life or
  busy result leaves no partial group row or lease.
- Resolution reads current-turn actions only, validates explicit targets before
  writes and advances through unique actor/turn rows plus session version CAS.
  Every action and timeout also requires the exact relational roster, current
  lives, DB session tuple, canonical current-turn actions and one session-owned
  `group-combat` lease per participant. Unknown rules, foreign/missing roster or
  lease ownership, malformed actions and inconsistent terminal results are
  repaired or CAS-invalidated as a rewardless proof. Repair is bounded,
  isolates unhealthy due rows and releases recoverable party/lease/timed-status
  ownership only after the winning terminal CAS.
- Win, loss and invalid terminal results always store zero XP, zero gold and no
  items. Character resources and economy remain unchanged; the party completes
  and every group-combat lease is released.
- `GROUP_COMBAT_PROOF_ENABLED=false` is default-off and hard-disabled in
  production. With the gate closed, no command, callback, help row or scheduler
  is registered. Non-production QA uses `/dev_group_combat <party-token>`.
- Each participant has one private-DM canonical card. Public party references
  are never reused and group/supergroup callbacks cannot mutate the proof.
  Combat-lock redirects refresh that recorded private card; group/supergroup
  routes receive only an inert pointer to the private conversation. Telegram
  edit/replacement remains post-commit; participant-scoped serialized
  authoritative reloads converge a durable content revision that includes
  queued actions. Per-participant delivery acknowledgements and a bounded
  rotating pending scan recover queued, terminal and repaired revisions after
  restart without repeatedly editing settled history. Inert replacement
  candidates are activated only after reference CAS, and a losing candidate
  stays inert even when Telegram deletion fails.
- Callback acknowledgements distinguish invalidated, missing, non-participant,
  missing-character and unavailable-actor outcomes instead of claiming that an
  action was recorded. Terminal integrity validation uses a durable per-session
  checkpoint: bounded passes reach unchecked immutable terminal rows on either
  side of healthy history across process restart without rereading validated
  rows on every scheduler tick. Missing result or completion metadata remains
  immediately repair-eligible.

## Measured budgets

Actual Prisma query-event fixtures on the final implementation:

- atomic start: `30` statements (`≤30` budget);
- queued non-resolving action: `18` statements (`≤18` budget), including the
  durable delivery-revision write;
- two concurrent duplicate final-action calls: `29` statements total
  (`≤35` per resolve-call budget);
- lean due-session id scan: `1` statement (exact budget).

A 13-session 3×3 simulation runs through the 25-turn cap with serialized active
state below `13,000` characters. A maximum proof card with a full bounded recap
fixture remains below Telegram's `4,096` character limit.

## Scope decisions

- `news.md` carries a spoiler-light foundation note for the numbered release;
  it does not claim that the non-production proof is a playable production route.
- Achievements, quest markers and lore are unchanged because the encounter is a
  hidden, rewardless engine proof rather than a discoverable production action.
- Full class/race/item parity, production rewards and Big Barrel migration remain
  follow-up work from `0.4.1`; they are not implied by this implementation.

## Manual Telegram QA

Use three local accounts. Start 2×2 and 3×3, choose different targets, allow one
timeout, restart between queue/resolution/delivery, try stale buttons and
restart/remort, kill different actors/enemies and finish win/loss. Confirm no
resources/rewards changed and no dev surface exists in production-like config.
The executable checklist is [`../qa/0.4.0-party-vs-many-proof-qa.md`](../qa/0.4.0-party-vs-many-proof-qa.md);
manual evidence is intentionally still pending.

## Release surfaces

- `0.4.0` version/changelog plus a spoiler-light news entry about the foundation,
  without exposing a production route or promising rewards.
- Architecture/design/task/QA/developer setup and compact AI context.
- No achievement, lore or quest change for a hidden rewardless proof.
