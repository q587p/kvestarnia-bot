# 0.2.11 — Combat Balance and Monster Signature Proof

## Goal

Ship a narrow combat-balance and monster-signature proof after player abilities, achievements, daily Korchma rounds and active cosmetic title selection. The point is to make ordinary PvE fights feel fairer and a few monsters more recognizably themselves, without opening party/raid runtime, rewards, economy, equipment rework or a broad monster-content expansion.

This is a proof slice, not a full combat rebalance. Use existing combat engine, typed monster ability runtime, battle journal, simulation tooling and content validation.

## Product intent

- Fights should still feel funny and risky, but not randomly oppressive after `0.2.7` player abilities and two-enemy escalation.
- A small selected set of current monsters should have more readable signature behavior in combat cards/journals: a named action, short Ukrainian consequence line, clear effect summary or recognizable telegraph where the existing ability runtime already supports it.
- Player-facing copy must stay compact and qualitative. Do not expose hidden formulas, exact odds, internal recipe keys or simulator-only data.

## Scope

- Run or extend combat simulation/reporting around current ordinary PvE fights after `0.2.7` abilities:
  - levels currently relevant to live play, at minimum `3..13`;
  - same-level ordinary fights;
  - one-enemy and two-enemy threat states where practical;
  - all active classes and a representative sweep of active races.
- Identify the smallest set of high-confidence balance adjustments from the evidence.
- Tune only bounded combat/content values needed for the proof, for example:
  - monster HP/attack/resist/armor bands;
  - selected monster ability coefficients/cooldowns/legal fallbacks;
  - selected player ability constants only if simulator evidence shows a clear outlier introduced by `0.2.7`;
  - presentation-only signature labels/flavor for selected monsters.
- Pick a tiny signature proof pack of current reachable monsters, preferably 5-8 across early/mid current play, and make their existing behavior read more distinct in active result cards and battle journal replay.
- Preserve deterministic injected-RNG/domain behavior and replay safety.
- Keep rewards, loot, XP, gold, Yeger progress, Adventure outcomes, Shynok economy, gifting, achievements, remort and equipment semantics unchanged unless the task doc explicitly records a tiny docs-only clarification.
- Update release/docs surfaces honestly.

## Non-goals

- No new party/raid runtime.
- No new combat session table, no schema migration unless current code proves an unavoidable tiny metadata need. Prefer no migration.
- No broad monster roster expansion.
- No new reward faucet, loot formula, Yeger integration, Adventure reward change or economy change.
- No equipment slot rework, item-instance rewrite, market, crafting, food, coffee or shop loop.
- No player title abilities, title combat buttons or cosmetic-title gameplay effects.
- No durable ability-use achievement counters in this release unless they are already fully supported by existing ledgers. Balance/signature visibility is not a reason to invent unverifiable historical counters.
- No exact hidden formulas in player-facing messages.
- No global rewrite of combat architecture.

## Acceptance criteria

- A short balance note in the PR body or task doc names what simulator/report command was run, what rough outliers were observed and why the chosen changes are small.
- Same-level ordinary PvE fights stay near the MVP intent in `docs/balance/notes.md`: short fights, ordinary win rate broadly around the intended band, and no obvious class/race outlier becoming the single correct build.
- Two-enemy ordinary threat fights remain harder than one-enemy fights but do not become an uncontrolled reward or death spiral.
- Selected monster signature proof pack has readable player-facing Ukrainian names/effects/telegraphs without raw ability ids, recipe keys or exact percentages.
- Battle journal/replay keeps stored outcomes stable; no old combat row is reparsed into new results.
- Impact signature lines render only when the stored monster skill actually applied an observable result: direct monster damage or stored effect text. Missed/no-effect stored skills may name the skill but must not invent consequence flavor.
- Unavailable/no-op player actions remain no-op: no turn, mana, cooldown, monster response, RNG advancement or reward mutation.
- No rewards, loot, XP/gold formulas, quest progress, Yeger/Shynok/gifting/remort/equipment/title-power semantics change.
- Content validation and focused combat tests cover changed monster/player ability constants and signature presentation.
- If no achievements are added, docs explain that this balance/signature proof does not add a durable player milestone. If a visible milestone is added, it must be rewardless and backed by a durable, replay-safe event.
- Release surfaces are in lockstep with `0.2.11` and the current Kyiv Holocene date.

## Balance note

Baseline aggressive same-level simulation over levels `3..13`, all classes, `race.human-ish`, 100 runs per matchup showed the post-`0.2.7` curve collapsing after level 5. Level aggregates were roughly:

- level 3: `84.6%`;
- level 4: `88.6%`;
- level 5: `74.3%`;
- level 6: `44.2%`;
- level 7: `35.9%`;
- level 8: `20.1%`;
- levels 9-13: roughly `7.9%`, `6.5%`, `2.7%`, `0.7%`, `1.3%`.

The chosen fix is deliberately small:

- flatten generic monster stat growth after the early ladder in `deriveMonsterCombatStats`;
- keep monster tag bonuses and authored monster abilities intact;
- tune only clear player ability outliers introduced by the current class/race ability surface: Warrior, Bureaucramancer, Rogue, Ranger and Priest constants;
- make the selected monster signature pack presentation-only from stored `monsterSkillId` / `monsterTelegraphAbilityId`.

Final validation:

- `npm.cmd run simulate:combat -- --levels 3-13 --monster-levels same --runs 100 --classes all --race race.human-ish --policy aggressive --seed 0.2.11-final-humanish-aggressive`
- Inline `runCombatSimulation` aggregate over all active races, levels `3..13`, same-level monsters, `30` runs per matchup, aggressive policy, seed prefix `0.2.11-final-race-sweep`.

Final human-ish aggregate: `43,200` runs, `84.2%` wins, `5.7` average turns. Level aggregates ranged from `74.1%` to `93.9%`; class aggregates ranged from Bureaucramancer `75.9%` to Rogue `94.4%`.

Final all-active-race aggregate: `116,640` runs, `80.3%` wins, `6.1` average turns. Race aggregates ranged from Bisyny `68.2%` to Elf `86.0%`. Remaining hard outliers are content-specific rather than a generic level-curve collapse: `monster.zero-declaration-tax-dragon`, `monster.siege-iron-varenyk` and some soft support/control race/class pairings still deserve future targeted tuning.

Two-enemy production threat state rewards and settlement logic were not changed. This slice covered two-enemy readability through presenter regression tests for stored multi-enemy monster skill responses; full two-enemy win-rate simulation remains a future tooling extension because the current simulator is one-enemy.

## Follow-up closure notes

No achievement hooks ship in `0.2.11`. This balance/signature proof changes how existing fights feel and read, but it does not add a durable player action, milestone, collection event or replay-safe counter. Adding achievement rows here would either be unverifiable historically or would reward a presentation-only visibility change.

No new `/dev_*` command ships. The slice does not add a new runtime gate, cooldown, timer, periodic ledger, random offer, pending session or once-per-period action; existing simulator commands and local fight/dev tools cover QA setup.

No remort/reset behavior changes ship. The touched state is combat formula/content presentation only; no new character ledger, quest counter, daily row, purchase limit or durable player state is introduced.

Starter/onboarding fallback paths are preserved. Level 1-2 starter combat remains outside this balance proof; the monster stat curve and signature presentation only affect existing combat rendering/runtime where those monsters/abilities already appear.
