# 0.2.0 - Safe Gifting MVP

Implemented in `0.2.0` after the Phase 2 MVP closeout was merged.

## Goal

Let one player offer exactly one eligible manatka stack unit to another player, with explicit recipient acceptance, transactional movement and replay-safe audit history.

## Scope

- Sender chooses one active same-location target through the existing nearby/presence surface.
- Sender chooses one eligible owned item stack and previews exact item, quantity `1`, target and expiry.
- The item button carries a compact server-derived selection guard for the exact `itemId` + item fingerprint shown on the card; create recomputes live eligibility and returns `stale-selection` instead of selecting a shifted list index.
- Server creates an opaque pending transfer token and reserves the whole `itemId` stack while the offer is live.
- A pending transfer reserves only until `expiresAt > now`; after passive expiry it stops blocking gift, Shynok sale, Mantok Chest and level-barter eligibility even if no callback was tapped. `processing` stays reserved until the transaction resolves.
- Recipient explicitly accepts or declines.
- Accept transaction rereads sender ownership, equipment, protection and competing reservations; moves one unit exactly once.
- Completed/declined/expired/cancelled callbacks replay canonical state.
- Add an audit row with frozen sender/receiver/item/result data.
- Block transfer while either participant has an incompatible active combat state or the sender has a pending progression/spend lock defined by the task.
- Player-facing copy is Ukrainian, short and clear that this is a gift, not a sale.

## Non-goals

- No item-for-item trade.
- No gold transfer.
- No market, auction, buyback or fees.
- No item-instance refactor.
- No gift power bonus, referral reward or quest progress.
- No equipped, priceless, story, protected, sentimental or reserved item.
- No public exact-location disclosure.

## Acceptance criteria

- Sender cannot offer an item unit they do not own.
- The offered `itemId` stack cannot be sold, recycled, bartered or gifted in another pending operation.
- Recipient ownership is revalidated.
- Accept is transactional and idempotent.
- Duplicate accept cannot move two units.
- Decline/expire/cancel releases the reservation.
- Untouched expired pending rows no longer reserve stacks, and old callbacks canonicalize them to `expired` without moving items.
- Remort/delete/restart paths leave no orphan active reservation.
- Stale preview after inventory/equipment/content change fails without mutation.
- Audit payload explains exactly what moved.
- Tests cover concurrent accept, duplicate callback, competing sale/chest/barter, decline, expiry and restart replay.

## Manual Telegram QA

1. Two characters enter the same place.
2. Sender offers one eligible unit.
3. Recipient accepts; sender loses one, recipient gains one.
4. Repeat old buttons; quantities do not change.
5. Try equipped/protected/story/reserved items.
6. Change stack/equipment before accept; transfer fails safely.
7. Decline, cancel and let one offer expire.
8. Try while one participant is in incompatible combat.
9. Restart between offer and accept; canonical state remains usable.
