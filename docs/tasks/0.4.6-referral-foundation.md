# 0.4.6 — Referral Foundation

Status: implemented on the `0.4.6` release branch; automated verification is recorded in the PR. Six-account Telegram QA, deployment and production flag state remain pending external evidence.

## Goal

Ship a default-off public referral loop with a deliberately strong, visible incentive: every accepted fresh direct invitee automatically gives the inviter an exact bundle of existing medical items, Iskrokamin and ordinary game gold when crossing the enabled level achievements at `3/5/8/13`.

The slice must preserve first-touch attribution and reward history at User level across restart/remort, automatically deliver each whole bundle to the inviter’s current Character exactly once, and coexist with every merged `0.4.5` start route, guild contract and `guild.created` Chronicle invariant through current `main` `4eeddf162a9b3858b4b9fb617b58cd0a99b5bd69`.

### Durable milestone and payout path

Add an additive Prisma migration and paired rollback for referral code, attribution, one stage-level bundle reward/receipt and durable notification evidence.

Required reward uniqueness:

```text
unique(attributionId, beneficiaryUserId, rewardFamily, milestoneKey)
```

Name the stage model `ReferralReward`. One row freezes achievement, plan version, `rewardGold` and a strict normalized `rewardItemsJson`; do not create one entitlement per component. Follow the live `DuelTournamentClaim.rewardGold + rewardItemsJson` persistence shape, then add the stronger referral CAS/outbox contract. Add a SQLite `rewardGold > 0` check plus strict service validation of the full JSON schema, positive safe integers, exact canonical order and unique item IDs. `rewardPlanVersion` is not part of uniqueness. Attribution/User evidence cannot cascade away. `grantedCharacterId` is nullable `SetNull`. Add `actualGrantJson`, `deliveryAttemptCount`, `nextAttemptAt` and a bounded non-sensitive `lastFailureCode`; initialize new rows due and use capped backoff for undeliverable rows. Add explicit indexes for `(inviterUserId,status,arrivedAt,id)`, payout `(state,nextAttemptAt,earnedAt,id)`, beneficiary wake-up `(beneficiaryUserId,state,nextAttemptAt,earnedAt,id)`, and outbox due/expired-lease scans plus its unique logical event key.

Extend `recordLevelMilestones` or an equally complete transaction-level canonical hook so accepted level crossings create User-level `PENDING` entitlements in the same gameplay transaction. Do not use best-effort achievement unlock rows as the payout receipt; restart deletes Character-bound evidence.

After commit, automatically project each pending reward:

1. re-read the exact owner-bound row in a short Serializable transaction;
2. resolve the inviter’s current Character;
3. strictly match the complete frozen bundle against the immutable policy version;
4. compare-and-set `PENDING → GRANTED` with Character/life evidence; zero rows must exit/roll back before economic mutation;
5. increment `Character.gold` and then every `CharacterItem` stack in deterministic `itemId` order;
6. store complete `actualGrantJson` and create one unique stage payout-notification outbox event;
7. commit before Telegram delivery.

Use bounded `P2034` retry and precise `P2002` handling consistent with current SQLite repositories; do not classify every item-stack creation collision as a replay. Gold delta, all item deltas, receipt, actual evidence and outbox commit together or all roll back.

No normal claim button exists. When payouts are disabled, restart leaves no current Character or a transient failure exhausts retries, keep the whole row pending. Retry immediately, after current-Character creation, on later inviter interaction and in a bounded due-time/keyset cold-start worker. Reschedule undeliverable rows so they cannot starve later due rewards. Remort keeps the same Character ID: serialize the whole bundle before or after its gold/item reset; no component may straddle it.

After grant, run ordinary best-effort `item.received` tracking from actual applied items and one `gold.balance` event from the committed `balanceAfter`, only for the winning grant. Do not emit `item.crafted`; tracking failure cannot roll back or replay the reward.

## Acceptance criteria

### Attribution

- An exact-shape, resolved and eligible fresh referral atomically creates the canonical User and one `PENDING` attribution before presence/onboarding upsert; unique-key races cannot backfill an independently created User.
- A failure between fresh User and attribution inserts rolls back both; retry never sees an orphan capture-created User.
- Exhausted transient capture conflict returns a neutral retry response before presence, leaves both User and attribution absent, and retrying the same valid link may capture atomically. A real concurrent User/attribution winner is re-read and classified from persisted state.
- The stable token has the exact 96-bit/16-character URL-safe shape, bounded collision regeneration and no raw-token logging.
- One invitee User has one first touch; self/existing/rebind/replay/race paths create no second relation.
- Accept and decline are terminal, owner-bound and idempotent.
- Accept/decline versus Character creation serializes; no `PENDING + Character` late acceptance or retroactive reward is possible.
- A legacy/inconsistent `PENDING + current Character` state fails referral acceptance closed while preserving ordinary play.
- Foundation-off pauses new capture/acceptance without changing accepted relations; invalid/disabled paths preserve ordinary onboarding.
- Raw payload/token is absent from logs, errors, callbacks, metrics and outbox.

### Rewards

- Exact `50/120/760/900` gold, `5/13/65/193` Iskrokamin and `1 dense + 1/2/3 field-kit` item grants come from one typed policy source. The complete track totals `1830` gold and `276` stones; level 8 combines the `+3` and `+4` costs and level 13 covers the maximum current legendary `+5` stone cost.
- Every canonical production level-changing path and supported local level accelerator creates the correct User-level stage rows.
- Level 8 jump creates `3/5/8`; duplicate event and reconciliation create none twice.
- Invitee restart/remort and repeat level achievement never reopen a stage.
- Plan v2 cannot reissue a stable stage.
- Plan v2 applies only to future acceptances; an already accepted attribution keeps its frozen plan for unearned, pending and granted stages.
- Concurrent automatic payout grants the complete bundle exactly once; a zero-row winner CAS cannot commit a gold or inventory change.
- Two distinct entitlements targeting the same gold balance and existing or absent CharacterItem stacks both accumulate without a lost update or mistaken `P2002` replay.
- Payout validates the full bundle against the immutable registry for its issued plan version. Missing/extra/duplicate/unknown items, malformed JSON, known-but-wrong item, wrong/non-positive/overflowing quantity or wrong/non-positive/overflowing gold stay pending, change no inventory/gold, send no received notice and emit bounded telemetry; never merge, clamp, substitute or discard a still-referenced policy definition.
- Missing current Character or disabled payout remains recoverable, not lost.
- Inviter restart before grant transfers pending delivery to the next current Character; restart after grant never reprojects the bundle. Remort serializes the whole grant before or after its gold/item reset and never reissues it.
- Ordinary item-received and gold-balance achievements may unlock; crafted achievements do not.
