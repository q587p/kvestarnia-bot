# 0.3.11 — Fight Turn and Daily Korchma Read-Path Reduction

## Goal

Reduce the two remaining measured database-heavy runtime paths without changing combat, quest, marker or Telegram behavior:

1. remove the unconditional Yeger progress pre-read from ordinary persistent `fight.turn` callbacks; and
2. replace the full Daily Korchma context lookup used by `main-menu.quest-markers` with a bounded marker read that reuses the already-started Fight result instead of loading a second full Fight overview.

This is one evidence-driven performance slice, not a combat rewrite or a Daily Korchma gameplay revision.

### `main-menu.quest-markers`

The window contains `77` complete quest-marker records. This is below the prior formal target of `100`, so it is not a precise population slow-rate estimate. It is sufficient for engineering direction because the bounded attribution splits into two non-overlapping cohorts with one consistent slowest source each.

| Population | N | Slow | Slow rate | p50 total | p95 total | Mean DB | Slowest source |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| All quest-marker calls | 77 | 38 | 49.35% | 343.2 ms | 605.0 ms | 341.5 ms | mixed |
| Eight sources | 25 | 0 | 0% | 118.5 ms | 231.4 ms | 126.3 ms | `fight` in 25/25 |
| Nine sources | 52 | 38 | 73.08% | 469.2 ms | 613.7 ms | 444.9 ms | `daily-korchma` in 52/52 |

The all-call slow-rate 95% Wilson interval is `[38.48%, 60.28%]`. It overlaps the earlier sanitized 0.3.8 aggregate broadly, so 0.3.11 must not claim that 0.3.9 already improved the overall slow rate. The lower observed DB mean is directionally positive, but the earlier baseline has no source attribution and the current window mixes materially different character-state cohorts.

The production source count confirms that the 0.3.9 top-level fan-out reduction is active: every call used eight primary sources, with a ninth source only for the existing conditional `cellar-grownup` lookup.

Code inspection explains the remaining slow cohort. `DailyKorchmaRoundService.getExistingForTelegramUser()` loads the full context in this serial shape:

1. character;
2. current offer;
3. full Fight overview;
4. pending Big Barrel state;
5. step rows when an offer exists;
6. reward row when an offer exists.

The main quest-marker snapshot has already started its grouped Fight source, so the Daily Korchma source repeats a full Fight overview. The marker itself only distinguishes `not-issued` and `turn-in-ready`; all other states intentionally render no Daily Korchma marker.

### `fight.turn`

The same window contains `80` complete `fight.turn` records:

| N | Slow | Slow rate | Slow-rate 95% CI | p50 total | p95 total | Mean DB | Mean Telegram | Measured latency share |
| ---: | ---: | ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 80 | 80 | 100% | `[95.42%, 100%]` | 705.2 ms | 1874.0 ms | 388.4 ms | 407.0 ms | 66.15% |

Telegram time is a material part of the route and is not controlled by this task. The controllable callback sequence still performs:

1. an unconditional full `YegerQuestService.getForTelegramUser()` pre-read on every turn, item and gear callback;
2. the authoritative Fight service resolution;
3. a presence write before the main Telegram edit;
4. a second Yeger read only after a newly won Yeger-relevant fight;
5. optional quest-progress, level-up and achievement messages.

The pre-read exists only to decide whether the post-fight Yeger progress card advanced. Most turns cannot end the fight, and most won fights are not Yeger-relevant, so this is controllable serial DB work on the common path.

## Engineering conclusions

- The 0.3.9 source grouping is live and the eight-source quest-marker cohort is healthy in this window.
- `daily-korchma` is the deterministic bottleneck for the nine-source quest-marker cohort and must be optimized as a marker read, not by caching the whole main menu.
- `fight.turn` remains the largest measured route by total latency share and has an unconditional Yeger read that is unnecessary on ordinary turns.
- Overall before/after percentiles are workload-sensitive. The implementation must prove removed calls with focused call/query-count tests and use bounded stage attribution for post-deploy diagnosis.
- Another full-day window is not required to choose this work. A later measurement is required only to quantify the shipped improvement.

## Scope

### 1. Daily Korchma quest-marker read

- Add a marker-specific Daily Korchma service result or read model used only by `main-menu.quest-markers`.
- Preserve the existing marker contract exactly:
  - `not-issued` produces the available marker;
  - `turn-in-ready` produces the ready-to-turn-in marker;
  - `no-character`, `level-locked`, `hp-blocked`, `active-fight`, `pending-barrel`, `ready` and `completed` produce no marker.
- Reuse the grouped Fight result already started by the quest-marker snapshot. Do not call `getFightOverviewForTelegramUser()` a second time from the Daily Korchma marker path.
- Do not serialize all remaining Daily Korchma reads behind Fight unnecessarily. Start independent marker reads concurrently where safe, then combine them with the shared Fight state.
- Read only the current-life/current-day Daily Korchma rows needed to distinguish the marker states. Do not build full scene/reward presentation data when the marker state can be decided without it.
- Preserve the existing optional fail-soft behavior. A Daily Korchma marker failure must not remove unrelated quest markers or change navigation.
- Keep `getExistingForTelegramUser()` authoritative for the actual Daily Korchma overview, scene, action and claim flows.

### 2. Persistent Fight turn path

- Remove the unconditional `getYegerProgressSnapshot()` call before every persistent turn, item and gear resolution.
- On a freshly updated, newly won Yeger-relevant fight, perform at most one post-win Yeger progress lookup and derive the same progress notification without a pre-read.
- Non-terminal turns, stale/duplicate callbacks, missing sessions, rest blockers and non-Yeger victories perform zero Yeger progress lookups from the bot callback layer.
- Preserve the existing problem-quest progress card, Yeger progress card, level-up celebration, achievement notification, callback alert and main fight-card edit ordering from the player's perspective.
- Keep Fight settlement, rewards, inventory consumption, cooldowns, combat leases, stored journals and replay behavior authoritative before any success presentation.
- Inspect the Fight service query sequence and remove at most one additional clearly redundant common-path read if focused repository-call evidence proves it can be removed without weakening active-session, CAS, settlement or replay guarantees. Do not turn this allowance into a repository or combat architecture rewrite.
- Keep presence semantics unchanged. Do not move an authoritative write after Telegram delivery. A presence timing change is allowed only if repository inspection and tests prove it is non-authoritative and failure behavior remains safe.

### 3. Bounded attribution

- Extend the existing privacy-safe performance record with the minimum bounded attribution needed to prove these reductions.
- For `fight.turn`, record an allowlisted DB-stage count plus one slowest DB stage and finite non-negative duration. Candidate labels are limited to `yeger`, `resolve`, `presence` and `reward-progress`.
- For the Daily Korchma marker source, record an allowlisted slowest internal stage only if service call/query-count tests cannot prove the production path unambiguously. Candidate labels are limited to `character`, `offer`, `fight-gate`, `barrel-gate`, `steps` and `reward`.
- Do not emit Telegram ids, player state, monster/item names, callbacks, SQL, dynamic labels, stack traces or raw production values.
- Attribution wall-clock durations may overlap and must not be presented as additive SQL time.

## Implementation result

- `DailyKorchmaRoundService.getQuestMarkerForTelegramUser()` is the bounded marker-only read. It loads only the current character, current-day offer, pending-Barrel gate, current-day step prefix and reward row required for marker state, consumes the already-started grouped Fight result and never calls `getFightOverviewForTelegramUser()`.
- Character and offer gates remain early exits; the independent pending-Barrel read runs concurrently with the shared Fight result, and step/reward reads run concurrently after an existing offer passes both blockers.
- `getExistingForTelegramUser()` remains the authoritative implementation for Daily Korchma overview, scene, action and claim paths.
- Persistent attack, defend, class-action, item and gear callbacks no longer perform a Yeger pre-read. Only a fresh won fight against a Yeger-relevant monster can call `getProgressAfterFreshRelevantWinForTelegramUser()` once; that lookup returns progress only while the just-counted win is still inside the active board target, preserving the old before/after notification eligibility without a pre-read.
- No additional Fight-service read was removed. Settlement, lease, CAS, reward recovery and replay evidence did not justify changing another authoritative read within this slice.
- `fight.turn` telemetry adds only a bounded DB-stage count and one allowlisted slowest stage/duration. Stage timings are non-nested wall-clock attribution and are not additive SQL time.

## Acceptance criteria

### Daily Korchma marker

- The production main-menu marker path never invokes a second full Fight overview from Daily Korchma.
- The shared Fight result and independent Daily Korchma reads are coordinated without turning the whole marker source into an avoidable serial chain.
- Focused call/query-count tests cover no character, level lock, HP block, active fight, pending Barrel, no offer, incomplete offer, turn-in-ready and completed states.
- `not-issued` and `turn-in-ready` markers are byte-for-byte equivalent at the keyboard/presenter contract; all other prior states still render no marker.
- A Daily Korchma marker failure remains local and unrelated markers survive.

### Fight turn

- Ordinary non-terminal attack, defend, class-action, item and gear callbacks perform zero Yeger progress reads.
- Stale, duplicate, missing-session and blocked callbacks perform zero Yeger progress reads.
- A fresh non-Yeger victory performs zero Yeger progress reads.
- A fresh Yeger-relevant victory performs at most one Yeger progress read and preserves the existing notification only when the current quest progress is eligible.
- Problem-quest progress, reward, level-up, achievement, presence, stored result and journal behavior remain unchanged.
- If one additional Fight service read is removed, focused tests prove identical active-session, lease, CAS, duplicate and terminal replay behavior.

### Telemetry and quality

- New attribution fields are bounded, allowlisted, finite and sanitized.
- Existing `fight.turn` and `main-menu.quest-markers` terminal telemetry still emits exactly one record on success and failure.
- Focused tests pass, followed by `npm run check`.
- The isolated manual-test bot is not stopped, refreshed or replaced during implementation.
