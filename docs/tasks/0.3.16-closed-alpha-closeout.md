# 0.3.16 — Closed Alpha Closeout

Status: implementation complete on the release branch; merge and target-environment evidence remain pending.

## Preflight

Fetch current main and live PR metadata. Start only when `0.3.15` is merged or
the human explicitly retargets this task. Verify behavior by tree/content, not
ancestry alone. Stop on version collision or unresolved `0.3.15` delivery/privacy
blockers; do not stack this work onto the raid-chat PR.

## Goal

Leave a lifecycle-safe, repairable and truthfully documented closed-alpha
baseline, then close `0.3.x`. This is a risk-driven closeout, not another themed
feature release.

## Scope

- Transactional `/restart` guard for every active combat lease, especially
  leader/nonleader in PartyBoss. Middleware remains explanatory only.
- Recommended initial `/remort` policy: block while a multi-actor combat is
  active. Preserve current solo semantics.
- Strict versioned PartyBoss state parser and idempotent repair for malformed
  sessions and orphan `party-boss` leases.
- Repair releases both Varenyk Sated and Bard Inspiration when recoverable; one
  malformed row cannot block healthy due work.
- Party capacity and resolution race coverage: final-slot join, duplicate final
  action, last two actions, action-vs-timeout and scheduler-vs-manual resolver.
- Lean current-turn action/due queries where evidence shows the current full
  historical include is on the hot path; no broad repository rewrite.
- PartyBoss support-ability decision: fix current class/race support parity and
  re-run balance simulations, or keep Big Barrel disabled and record the exact
  blocker/owner before closeout. Never expose a spend-action no-op as supported.
- Complete `docs/operations/release-state-ledger.md` from real target evidence.
- Privacy-safe aggregate closed-alpha funnel/report and an explicit feedback /
  admin-allowlist decision. Reuse current event/data sources; store no message
  content and expose no individual player report.
- Risk-based Telegram QA, backup/restore/migration proof, rollout/rollback notes,
  production observation window and canonical documentation sync.

## Non-goals

- New quests, rewards, economy, guilds or party-vs-many gameplay.
- Big Barrel migration to generic group combat.
- Broad `FightService` decomposition, Redis or Mini App work.
- Enabling every default-off flag.
- Backfilling or claiming manual checks that were not run.
- A free-text moderation platform; a safe feedback link/category route is enough.

## Acceptance criteria

1. Restart command and confirm callback cannot delete a leader or nonleader in an
   active multi-actor combat. The authoritative DB transaction returns a typed
   busy result and preserves session, roster, actions, leases and character.
2. A delete-vs-resolve race has one safe winner and cannot create orphan leases,
   ghost participants or a missing active session.
3. Remort is blocked transactionally during active PartyBoss. Replays and races
   preserve existing solo behavior and do not cancel another player's raid.
4. Strict PartyBoss parsing rejects non-object, partial, rules/turn/party mismatch,
   duplicate/missing roster and invalid numeric state. Repair is CAS/idempotent,
   gives no rewards and releases recoverable leases/statuses.
5. An orphan `party-boss` lease is repaired; a corrupt due row does not stop a
   healthy row in the same scheduler pass.
6. Concurrent final-slot joins never exceed capacity. Last-action/timeout races
   advance one turn, consume each item at most once, create one activity/
   achievement source and settle one terminal plan.
7. Current-turn resolution does not load all historical actions. Lean due scans
   and state/card size remain bounded on the hosted baseline.
8. Current PartyBoss class/race support actions either have tested intended
   effects and updated simulation evidence, or are not available in the target
   rollout and the ledger names the follow-up owner.
9. Every default-off surface has explicit merged/migrated/flag/automation/manual
   QA/kill-switch evidence and final `enabled`, `deferred` or `retired` decision.
10. A privacy-safe aggregate report covers creation, D1/D7, first-day PvE, duel
    accept/rematch and party create/join/start/finish where data exists; missing
    instrumentation is named, not fabricated.
11. Feedback and admin allowlist each have an explicit implement/defer/retire
    decision consistent with the actual closed-alpha channel.
12. Migration/backup/restore, `npm run check`, combat simulations, focused race
    suites, manual Telegram matrix and observation window are recorded honestly.
13. README, roadmap, product brief, game design, technical plan, task index and
    compact AI context match the release-state ledger and `0.4.x` cutline.
14. Package/changelog/news/version surfaces call this the final `0.3.x` closeout;
    no feature is described as production-playable without target evidence.

## Implementation record

- `/restart` now performs one transactional conditional delete against the active
  combat lease and returns a typed `active-combat` result. `/remort` blocks an
  active PartyBoss instead of cancelling the shared encounter.
- PartyBoss state uses a strict rules/turn/party/roster/numeric parser. Malformed
  active rows are CAS-cancelled without rewards, recoverable Sated/Inspiration
  state is released, and a bounded anti-join query repairs orphan leases without
  letting healthy active leases starve the scan. Stored rounds reject invalid
  optional Ward counters, action enums, participant resource/status pairs and
  other runtime-read fields before a corrupt value can reach presentation.
- PartyBoss start freezes a joined participant at zero HP as `knocked-out`
  instead of creating an invalid active snapshot. Mixed rosters continue with
  their healthy members; an all-zero roster settles as a normal rewardless loss
  on its first due turn. A failed scheduled recruiting start is isolated per row,
  so later recruiting rows and active-turn timeout work still run.
- Current resolution loads at most the newest 13 queued action rows and keeps only
  the latest round in hot state; append-only `PartyBossRound` rows retain every
  journal page without unbounded state rewrites. The due scan first selects a bounded set of due ids. Race coverage
  owns final capacity, concurrent last actions, duplicate final actions,
  action/timeout/scheduler overlap and delete/terminal-resolution safety.
- Current class/race support scopes work in PartyBoss: ally healing, multi-ally
  protection and targeted counter response are stored and presented. Big Barrel
  base retaliation increased by one point; the seeded regression bands remain
  `35–49%` for the prepared uneven party and `75–93%` for a full same-level party.
- Persistent fights now carry the attempted `skill`, `race` or `gear` source into
  blocked-action presentation. Shared copy helpers keep ordinary fights and
  turn-based duels from calling a class or race cooldown an equipment action;
  Training keeps its intentionally neutral wording and PartyBoss retains its
  genuinely gear-only unavailable-action notice.
- Production-log follow-up found two coupled latency defects in the multi-player
  path. PartyBoss and raid-chat recipient fan-out awaited Telegram network calls
  inside grammY's sequential update loop, while every 1.1-second raid-chat tick
  also performed idle maintenance writes. Recipient pushes now run in bounded
  background work, retain per-raid turn order, and maintenance runs every 42
  seconds after due delivery. Existing participant delivery rows are dirtied by
  one set update instead of one upsert per participant.
- A resolved PartyBoss action is now the only transition that fans out a new
  combat card. Late callbacks that observe the already-terminal session still
  return the canonical final view to their sender but never broadcast that same
  terminal turn to the whole roster again. This directly covers the observed
  repeated `Бій: 17 хід` incident.
- The Kharakternyk ward sign now uses `✴️` consistently on its placement button,
  confirmation, lobby state, active card and stored result lines. The Molfar
  `🧿 Туманний оберіг` keeps its existing icon, so adjacent raid concepts no
  longer share one marker.
- Player `/help` now opens a compact index and five inline-paginated pages:
  Character, Adventures, Manatky, Korchma/people and reference/news. Every
  available public command belongs to exactly one page, feature-gated table
  games stay gated, dev commands remain excluded, and the read-only callbacks
  remain available through an active combat lock.
- The equipment overview now keeps its first keyboard compact: one explicit
  `Змінити спорядження` action opens the existing seven slot filters and occupied
  slot removal controls; the compact view does not duplicate the persistent
  Manatky navigation. The expanded view returns to the compact overview, and
  successful unequip actions keep the controls open for another change.
- The accepted Charkokovalnia access affair no longer reports itself as a fresh
  `CAN_ACCEPT` marker while its field kit is missing. Its Quest Table, hall and
  yard routes stay unmarked during active progress; owning the kit still raises
  the existing `CAN_TURN_IN` marker.
- Explicit Cellar navigation now bypasses the command-only Korchma-interior gate:
  `У льох` and place callbacks open the cellar and persist its presence even when
  an older card is pressed after the player moved outside. `/cellar` keeps the
  existing interior requirement.
- Daily Korchma Round scene and action-result keyboards derive their return route
  from the authored scene location. The yard, hall, Quest Table, Shynok, Barrel,
  Cellar, news board, both corners and Nyz now expose distinct named return buttons
  instead of every completed action pointing to the hall.
- PartyBoss round settlement now appends each resolved summary to paginated
  historical rows and keeps one latest summary in the hot state. Existing journal
  presentation and first/back/next/end callbacks reach every newly stored turn,
  including fights longer than 13 rounds, without loading the full journal on each action.
- The unreleased round-history migration backfills `leaderCharacterId` into
  legacy terminal state JSON before relational re-anchoring can occur. A real
  pre-migration fixture proves that leader restart preserves the original frozen
  leader, terminal result and all 25 journal pages. The unique `(sessionId, turn)`
  index remains the only round-history index on that prefix.
- Personalized Adventure and starter-quest results now collapse identical
  race/class technique beats before composing a signature outcome. This fixes
  the observed Elf Rogue exam result that repeated one sentence twice, replaces
  the player-facing internal `Фінес` term with a natural exact-movement sentence,
  and rewrites technical title-result phrasing as an in-world signature.
- `npm run report:closed-alpha -- --from=<ISO> --to=<ISO>` is a read-only,
  aggregate-only report. It reads immutable `ActivityEvent` rows only when their
  occurrence is inside `[from, to)` and the ledger row was recorded before `to`,
  so later backfills and character restart cannot alter an older report. Exact
  acquisition, D1/D7 retention, first-day PvE, duel acceptance/completion/rematches
  and party funnel KPIs stay `null` where historical coverage is uncertified;
  separately named recorded-event counts expose only the evidence that exists. It
  emits no Telegram ids, character ids, names or message content.

## Product and rollout decisions

- In-bot free-text feedback: **deferred**. No moderation/content storage surface
  is added in this closeout; the operator must name an external closed-alpha
  category/channel before inviting a wider cohort.
- Player admin allowlist: **retired for 0.3.x**. Existing admin command ids remain
  operator authorization, not an inferred player allowlist. Future invite gating
  requires a separate explicit task.
- Achievements: no new definition. The support buttons already existed; 0.3.16
  fixes their PartyBoss effect, while Help remains an existing non-gameplay
  reference surface rather than a new rewardable player action.
- Quest overview: the existing Charkokovalnia row and route remain available, but
  its active marker now matches the already-accepted state until the field kit is
  ready for turn-in. Its existing Cellar route now reliably reaches the location
  from a stale card. Lore: no update; route recovery does not change in-world canon.
- The blocked-action label correction adds no achievement, quest-overview, lore or
  remort change: it only identifies an existing combat action by its actual source.
- The compact equipment control is navigation over existing equip/unequip actions,
  so it adds no achievement, quest-overview, lore, remort or dev-helper change.
- Full PartyBoss journal retention changes only stored replay detail for the
  existing combat loop. It adds no reward, achievement, quest, lore, remort or dev
  helper; one forward-only migration adds append-only round history.
- The Cellar route fix adds no achievement, state, timer, reward, remort or dev
  helper; it only separates explicit movement callbacks from the `/cellar` gate.
- The Daily Korchma Round return-route fix adds no achievement, quest-overview,
  lore, state, timer, reward, remort or dev-helper change; it uses the scene
  location already present in the authoritative service result.
- Dev helper: no new timed player loop was added. Existing PartyBoss/dev fixtures
  cover manual setup; the new alpha report is a read-only operator command.
- Remort/reset: no new persistent player state was introduced. The report stores
  nothing, repair removes orphaned life-bound leases, and PartyBoss remains blocked
  until its shared encounter settles.
