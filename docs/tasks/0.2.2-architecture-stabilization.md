# 0.2.2 — Architecture Stabilization

Draft versioned implementation task.

If `0.2.2` has already shipped when work starts, use the next free `0.2.x` version and rename versioned release surfaces without changing this task's feature scope.

## Goal

Make the Telegram runtime and production composition easier to change safely before Threat Escalation and later social-combat work.

Convert the central bot assembly into explicit feature registrars, extract cross-cutting middleware, and split dependency construction/lifecycle out of the executable entry point.

This is a behavior-preserving runtime refactor.

## Scope

### Bot contracts

- Move `BotServices` out of `src/bot/createBot.ts`.
- Move `BotOptions` out of `src/bot/createBot.ts`.
- Keep contracts explicit and typed.
- Do not introduce a generic service locator.

### Middleware

- Extract combat-lock middleware and its private redirect helpers to a dedicated bot middleware module.
- Extract presence middleware registration to a dedicated module.
- Extract the pending-raid guard helper only if it remains a narrow helper.
- Preserve middleware order and all route allow/block behavior.

### Feature registration

- Split command/callback registration into 5–8 coarse feature registrars.
- Each callback namespace must have exactly one registrar owner.
- Keep registration order explicit in `createBot.ts`.
- Move feature callback handlers with their registrar where practical.
- Existing command, parser, keyboard and presenter files should remain reusable.
- A tiny typed callback-registration helper is optional, not required.

### Composition root and lifecycle

- Add a small `src/app/` layer for repository creation, service creation and runtime lifecycle.
- Keep manual dependency injection.
- Move direct Prisma repository/service construction out of `src/bot.ts`.
- Start health server, polling, schedulers and deploy notifications through explicit runtime lifecycle ownership.
- Preserve BOT_TOKEN-missing behavior, shutdown behavior, Telegram menu synchronization and best-effort deploy notifications.
- Keep the isolated local bot workflow unchanged.

### Architecture tests

Add focused tests for:

- domain import boundaries;
- `createBot.ts` orchestration-only imports;
- `src/bot.ts` delegation to application factories;
- expected feature registrar invocation;
- representative combat-lock routes;
- representative presence routes;
- pending-raid safe and blocked routes;
- disabled optional features;
- runtime start/stop behavior where practical.

### Release documentation

Update the required version surfaces and architecture documentation. Keep player news short and non-technical.

## Acceptance criteria

### Behavior parity

- Existing commands and callback namespaces remain registered.
- grammY middleware and route registration order remains behaviorally equivalent.
- Invalid callbacks keep the same alert/edit behavior.
- Active combat lock keeps the same allowed and blocked routes.
- Pending Barrel raid gates and read-only bypasses remain unchanged.
- Presence writes remain unchanged for commands, callbacks and reply-keyboard text.
- Optional duel, Shynok, gift, remort, dev and notification behavior remains unchanged.
- Startup, BOT_TOKEN-missing mode, health server, schedulers and shutdown remain equivalent.
- No player-visible copy changes except required release/news metadata.

### Structure

- `src/bot/createBot.ts` is an orchestration shell.
- It directly imports no feature presenter, keyboard or callback parser.
- `src/bot.ts` directly constructs no Prisma repository or gameplay service.
- Feature registrars do not construct repositories/services.
- One callback prefix is registered in one place.
- Cross-cutting middleware has named modules and explicit ordering.
- `src/domain/**` remains free of grammY and bot-layer imports.
- No new circular dependency is introduced.
- No production dependency, schema or migration change is present.

### Test and release gate

- Baseline behavior tests pass before movement.
- Focused tests pass after every major checkpoint.
- `npm run db:validate` passes.
- `npm run check` passes.
- `git diff --check` passes.
- Manual Telegram smoke is recorded.
- The branch is merge-ready against current `main`.
- Final PR scope contains no feature or balance changes.
