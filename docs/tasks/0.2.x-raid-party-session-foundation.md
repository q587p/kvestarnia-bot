# 0.2.x - Raid Party Session Foundation

Rename `0.2.x` to the next free version only when implementation starts.

## Goal

Add a restart-safe, concurrency-safe group raid recruiting/session foundation that supports one leader plus up to seven joiners through nearby targeting and one opaque deep link, while production Barrel behavior and rewards remain unchanged.

## Prerequisites

- Start from current `main` after the intended architecture stabilization point.
- Re-read the shipped multi-enemy/combat application boundaries instead of assuming an old branch shape.
- Do not combine this task with Senior Barrel Brother production combat.

## Scope

- Add relational group raid session and participant persistence through a new migration.
- Implement statuses `recruiting`, `cancelled`, `expired`; reserve future-safe active/terminal values without shipping combat transitions.
- Create exactly one live recruiting session per leader and one live membership per character.
- Capacity `8`, explicit minimum metadata `1`.
- Opaque server token and compact `/start` deep-link preview for the exact session, preserving its frozen Barrel period across wall-clock bucket changes.
- Join, idempotent rejoin, leave, leader cancellation, deterministic leader transfer and passive expiry.
- Targeted invite action from the existing `👀 Хто поруч` surface, with best-effort private delivery.
- Dev-only or disabled-by-default entry point to create and inspect sessions.
- Feature flag/config seam for later production activation.
- Short Ukrainian cards and callback parsers under Telegram limits.
- Restart-safe lookup and stale callback replay.
- Narrow dev helpers to advance/expire a recruiting session for QA.
- Documentation and tests for the foundation only.

## Non-goals

- No production level-8 route.
- No boss, combat rounds, HP, mana, abilities, adds or combat leases.
- No XP, gold, items, success gate, beer access or economy change.
- No readiness vote, kick, matchmaking, guild, permanent party, spectator mode or public roster.
- No general party abstraction used by every game mode.
- No Telegram group-chat requirement.
- No Redis/BullMQ.
- No version-number guess beyond the chosen actual implementation version.

## Required invariants

- Duplicate create converges to the same canonical live session.
- One character cannot be live in two raid sessions.
- Concurrent joins never exceed `8`.
- Join at/after expiry cannot revive the session.
- Duplicate join does not create two participant rows or notices.
- Leave clears the live membership exactly once.
- Leader leave transfers deterministically to the earliest joined remaining participant.
- Last participant leave/cancel terminalizes the session and clears live keys.
- Opaque tokens reveal no ids or trusted eligibility data.
- Nearby filtering/invites do not reveal exact locations or private rejection reasons.
- Old and forwarded buttons replay canonical state.
- Restart does not lose membership or create a second session.

## Suggested data shape

Use `docs/architecture/GROUP_RAID_SESSION_MODEL.md` as design input, then adapt names to current repository conventions. The authoritative minimum is one session table plus one participant table with unique live keys and indexes for expiry/status lookup.

Do not make `User.currentRaidId` authoritative without first proving its current semantics and migration compatibility.

## Acceptance criteria

- Dev entry creates a canonical recruiting session with leader membership.
- A second account can join from a copied deep link.
- An eligible nearby target can receive and accept the same session invite.
- Replaying join returns current roster without duplicate membership.
- Eight accounts can join; two concurrent ninth attempts receive controlled full/stale results.
- A member can leave; leader transfer is deterministic and reflected on every refreshed card.
- Last-member leave or leader cancellation terminalizes without orphan live keys.
- Expiry before/after restart is canonical and cannot be reopened by old links.
- Session/participant HTML escapes dynamic names.
- Production level `1–13` Barrel route, rewards, notifications and beer gate are byte-for-byte or behaviorally unchanged except intentional shared helper extraction.
- No combat/economy code is activated from this foundation.

## Manual Telegram QA

1. Enable dev commands/feature flag locally.
2. Create a session as account A.
3. Join as B through deep link; replay the link.
4. Invite C through `👀 Хто поруч` and accept privately.
5. Verify roster names but no private ids/locations.
6. Leave as B; rejoin.
7. Leave as leader A; verify deterministic new leader.
8. Fill to 8 and attempt two simultaneous extra joins.
9. Restart while recruiting; refresh all cards.
10. Expire via dev helper; replay every old button/link.
11. Disable flag/dev commands; verify no production player can create the foundation flow.
12. Run ordinary Barrel start/complete and beer access unchanged.
