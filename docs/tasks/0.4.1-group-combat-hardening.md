# 0.4.1 — Group Combat Hardening

Status: implemented on `codex/0.4.1-group-combat-hardening`; automated gates
recorded below, manual Telegram QA pending on the final exact head.

## Goal

Bring the generic 3×3-bounded runtime to current combat feature parity and leave
an idempotent per-player settlement skeleton ready for the first production
expedition.

## Scope

- Pure deterministic support/target resolver for current self/ally scopes.
- Current class/race recipe parity: heal, guard, response reduction, counter,
  cooldown, mana, fumble and unavailable-action semantics.
- Multi-enemy AI/targeting, status and threat rules authored for the proof bounds.
- Supported gear/item actions with explicit target policy and exact-once consume.
- Participant resource/contribution/reward settlement-plan rows with a zero-reward
  proof policy and independently retryable receipts.
- Full strict parser/repair/lease/status lifecycle and scheduler observability.
- Query/card/state budgets, concurrency matrix and combat simulator coverage.
- Player-facing action/readability copy only on the flagged proof surface.

## Non-goals

- Production reward values or economy changes.
- New classes/races/abilities/items.
- Guilds, matchmaking, >3×3 or Big Barrel migration.
- Making every solo-specific threat/escalation rule generic.

## Acceptance criteria

1. Priest, Bard, Varenyk-mancer, Dwarf, Domovyk and Molfar matrix tests prove
   intended target/effect behavior; no supported action spends a turn for no
   authored effect.
2. Lowest-HP and all-allies targeting is deterministic with stable tie-breaks;
   dead/ineligible targets never receive support.
3. Enemy AI chooses only legal living targets, handles multiple deaths and
   preserves stored deterministic replay.
4. Supported item/gear use is atomic with action claim and consumed once under
   duplicate/last-action/timeout races.
5. Terminal resolution creates one immutable settlement plan. Each participant
   zero-reward receipt replays independently; partial retry cannot mutate combat.
6. Contribution includes damage, healing, guard prevented, control, damage taken
   and committed actions without double counting.
7. Parser/repair covers every new recipe/status/target form and releases all
   frozen timed states at terminal/invalid repair.
8. Simulator covers classes/races, 2×2/3×3, 13/25 turns and target policies with
   explicit invariants rather than a single win-rate target.
9. Concurrent sessions meet documented query/state/card budgets. No due scan or
   action submit loads unbounded history or sends a new card each round.
10. Existing solo, turn-duel and Big Barrel behavior remains green; any shared
    primitive change includes parity tests and fresh Big Barrel balance evidence.

## Implemented contract

- `group-combat.v2` freezes class, race, effective stats, supported equipment
  abilities and bounded supported-item quantities beside the accepted 3×3
  actor snapshot. It keeps the proof flag default-off, production-hard-disabled
  and rewardless.
- One pure resolver owns deterministic self, explicit ally/enemy, lowest-HP and
  all-target policies. Stable HP-ratio ties use roster/enemy order; dead or
  ineligible targets are excluded. Every committed supported single-enemy
  class/race/gear action retargets to the stable first living enemy if its
  selected enemy died earlier in the round; an already-finished enemy roster
  cannot spend a later actor's mana, cooldown or committed action.
- With proof helpers enabled, `/dev_party` creates a separate 2–3 participant
  GroupCombat gathering capped at three entries and due three minutes after
  creation. The bounded scheduler starts it from the current eligible roster
  without a button or command; the leader button and `/dev_group_combat` remain
  optional early-start paths. After terminal resolution, a stale private
  recruiting card renders the participant's real rewardless combat result and
  journal controls instead of a generic archive notice. Public and
  non-participant cards reveal no combat result.
- Current class/race profiles reuse the shared actor action primitive for mana,
  cooldowns, hit/fumble and committed-action semantics. Guard, aid and item use
  also advance existing ability cooldowns. Exact effect coverage includes
  Priest healing only the lowest-HP ally while its authored guard/response
  mitigation covers all living allies, plus counter victory at the turn cap.
- Multi-enemy AI ranks living participants by threat, then HP ratio and roster
  order. It recalculates after each response, so a participant killed by one
  enemy cannot receive the next response. Guard, response mitigation, counter
  and bounded gear bleed are strict status forms.
- The existing three combat healing items are self-targeted proof actions.
  Their server-owned item id is stored on the action row; the inventory
  decrement and state/turn CAS share one transaction. Canonical bounded state
  preserves the Dense Bandage five-own-action cooldown and Field Kit
  once-per-fight marker. If live inventory loses a frozen committed item, the
  attempted resolution rolls back and a separate CAS invalidates the proof
  rewardlessly. That CAS rewrites every relational contribution and settlement
  field to the exact fallback state, validates the complete terminal graph
  before marking integrity, releases leases/statuses exactly once and remains
  loadable, deliverable and terminal on replay.
  Frozen supported Mantok gear actions use the same actor/turn uniqueness and
  state cooldown ownership.
- A terminal CAS stores one immutable zero-reward settlement plan. Each
  participant receipt has an independent CAS and exact replay; receipt retries
  do not mutate combat or Character economy/resources. Plan rows must equal
  canonical terminal state and relational identity/order/contribution exactly;
  status/receipt pairs and every receipt's session, character, remort and
  zero-reward plan entry are checked before settlement or replay. Shape-valid
  altered artifacts are rebuilt canonically and remain unchecked until a later
  clean integrity pass. Formerly-active invalidations use one canonical pending,
  zero-attempt, receipt-free participant policy, including malformed rows,
  wrong-lease repair and `group-combat.v1` upgrade repair. Strict validation
  rejects any pending row unless attempts are exactly zero and receipt/settledAt
  are null; terminal repair canonicalizes that row before a later clean pass may
  set the integrity checkpoint, while completed rows retain their canonical
  receipt, positive attempts and settledAt.
- Normal active/won/lost proof state and settlement plans remain capped at
  three participants. Repair-only `invalid` state and plans may preserve up to
  13 exact relational participants within the same 32,768-byte state cap. If
  corruption exceeds that bound or a row cannot fit the strict representation,
  repair keeps the earliest representable rows in stable roster/id order,
  releases every session-owned lease and recoverable frozen status, removes
  discarded participant rows, then validates and integrity-checks the remaining
  canonical rewardless graph in the same transaction.
- Contribution records actual damage, healing, guard prevention, control
  prevention, damage taken and committed actions. Terminal cards render those
  dimensions rather than eligibility or reward claims.
- `group-combat.v1` rows are non-production proof data. After the rules upgrade,
  the strict repair path invalidates such rows rewardlessly and releases leases
  plus recoverable frozen timed statuses.

## Budgets and automated evidence

- Query-event budgets/observations: start `32/32`, queued action `20/20`,
  direct single resolving action `22/35`, concurrent duplicate-final pair `31`
  aggregate, due-id scan `1/1`. The two added start reads freeze only the
  allowlisted item rows for the bounded roster.
- State cap: `32,768` UTF-8 bytes. The required 24-case simulator matrix
  observed a maximum of `5,066` bytes. Every requested 13-turn case completed
  exactly 13 turns and every 25-turn case exactly 25; every support profile was
  observed unavailable and then reusable after its authored cooldown, and the
  rewardless assertion is derived from each real terminal settlement plan.
- Card cap: `4,096` UTF-8 bytes. Cards reuse canonical messages, keep only five
  recap turns and drop the recap from the live/result card if needed before
  exceeding the cap; the maximal-card regression fixture measured `1,637`
  bytes. Strict callback data remains capped at `64` bytes; the maximum accepted
  v2 action fixture measured `46`.
- Generated `v2:gc:a:*` buttons pass combat-lock middleware and the real social
  module route exactly once. The strict parser accepts only the generated
  eight-segment v2 action form with `optionIndex`; only the intentionally retained v1
  start/view/journal/back forms remain compatible; malformed cross-version
  forms fail the strict parser.
- Focused domain/parser/presenter/service tests cover target ties, support
  recipes, unavailable actions, fumbles, threat, multiple deaths, contribution,
  gear/item payloads, state/card bounds and immutable settlement artifacts.
- Prisma integration covers item/final-action/timeout overlap, exact-once
  consume, immutable terminal plans, independently replayable receipts,
  nonzero-round inventory drift, canonical invalid participant rows, realistic
  v1 upgrade repair, malformed action/state repair, lease/timed-status release,
  restart/remort blocking, delivery replay, due isolation and deterministic
  query attribution. The final corruption follow-up adds a four-row relational
  roster with nonzero contributions/foreign settlement metadata and a 14-row
  overflow fixture; focused parser/domain/delivery/repository coverage passed
  226 unit tests and focused repository coverage passed 99 integration tests.
  Pending-attempt canonicalization covers active `13`/`-1`, terminal two-pass
  integrity and completed replay; the full gate passed 4,069 unit plus
  606 integration tests.
- The GroupCombat simulator is appended to `npm run simulate:combat`; it asserts
  deterministic replay, legal living targets, exact committed-action totals,
  bounded state and zero-reward terminal plans rather than a win-rate target.
- Focused lifecycle/presentation coverage proves the three-minute 2–3 gathering
  contract, automatic due start with the current roster, invalid-size expiry,
  private stale-card terminal replay and public-card non-disclosure.
